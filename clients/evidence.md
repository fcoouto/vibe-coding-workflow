# Task checks and review evidence

Load this contract for a Codex task that needs accepted checks, general or security review, a completion decision, or local merge evidence. Follow the full [Tests and Builds](../policies/05-tests-and-builds.md), [Code Review](../policies/06-code-review.md), and [Security Review](../policies/04-security-review.md) contracts; this file gives the local controls, not replacements for those policies. This is task runtime guidance: do not load Toolkit sources, setup/onboarding procedures, or Superset guidance.

## Plan and capture

Use the installed package's `scripts/workflow.py` with the enrolled checkout as `--cwd`. Mutations take the current Codex client/session/task/scope identity and `expected_revision` as bounded JSON on stdin. Start and update controls remain in [task runtime](runtime.md). Evidence operations are:

```sh
python3 -I -B /path/to/package/scripts/workflow.py evidence plan --cwd /checkout < plan.json
python3 -I -B /path/to/package/scripts/workflow.py evidence status --cwd /checkout --client codex --session SESSION
python3 -I -B /path/to/package/scripts/workflow.py evidence check --cwd /checkout < check.json
python3 -I -B /path/to/package/scripts/workflow.py evidence reconcile-check --cwd /checkout < reconciliation.json
python3 -I -B /path/to/package/scripts/workflow.py evidence review prepare --cwd /checkout < prepare.json
python3 -I -B /path/to/package/scripts/workflow.py evidence review collect --cwd /checkout < collect.json
python3 -I -B /path/to/package/scripts/workflow.py evidence review assess --cwd /checkout < assess.json
python3 -I -B /path/to/package/scripts/workflow.py evidence verify --cwd /checkout < verify.json
```

The plan records acceptance criteria, accepted command definitions and thresholds, execution limits, baseline, candidate/base comparison, exclusions, and risk-based review applicability. Preserve `required`, justified `inapplicable`, or `unresolved` for each review scope; lack of a tool or reviewer is unresolved. Every completed change needs an assessed security impact. Do not invent commands or treat request JSON as permission to change thresholds or authorize side effects. Use existing decision references for accepted rules; a changed rule needs the established decision process.

Checks run only the planned argv and environment, without shell interpretation or inherited credentials. Review collection verifies the prepared task marker in native parent/child records, child checkout, completed turn, and fetched final report. The native prompt is encrypted and is not claimed as observed; receipt proves execution identity, not review quality or read-only enforcement. The coordinator must check semantic coverage and findings against the target. Keep detailed snapshots, output, and reports in the private evidence area; records contain bounded summaries and digests, never raw transcripts or secrets.

## Request fields

Every mutation JSON object includes `client:"codex"`, `session_id`, `task_id`, `scope_ref`, and current positive `expected_revision`. Use the revision returned by the previous operation; after a conflict, read status and prepare a fresh request. JSON input is limited to 128 KiB; unknown fields reject.

`evidence plan` takes `plan` with version 1 and these required fields: `decision_ref`; `criteria` (`id`, `checks` command IDs, `behavior` boolean); `checks` (`id`, exact `argv`, relative `cwd`, `timeout` 1–300 seconds, explicit credential-free `env` containing `PATH` and optionally `LANG`, `LC_ALL`, `TZ`; `effects` with `kind` read-only/disposable, `inspection_ref`, and `network`, `production`, `publish`, `migrations` all false; `baseline` status passed/failed/not-run and reference; relative `dependencies`); `reviews` for `general` and `security` with `applicability` required/inapplicable/unresolved, reason, and independent boolean; `security_impact` status assessed/unresolved, reason, reference; `base`, `comparison` endpoint/merge-base, `nontrivial`, absolute safe `instructions`, relative `exclusions` with impact, and `review_limit` 1–8. There must be 1–32 criteria; checks may be empty only when behavior is observed, otherwise include up to 32 accepted commands. Optional `relevant_untracked` lists relevant ignored paths; optional check `thresholds` can only be `{"exit_codes":[0]}`. A comparable failed baseline may include its integer `exit_code` and SHA-256 `output_digest`; only an exact signature match is pre-existing, otherwise failure comparison remains unresolved. Changing accepted rules requires `change_decision_ref`.

`evidence check` requires `check_id`. It runs that exact planned command. Output is private, bounded to 128 KiB, and common credential lines are redacted. Observed outcomes remain pending lifecycle reconciliation: a parent exit or empty process group cannot prove detached descendants stopped. A failed check can be retried after its lifecycle is reconciled and its result addressed or understood; introduced failures block. Changed inputs, timeout, overflow, or uncertain surviving processes do not pass.

`evidence reconcile-check` requires `attempt_id` and `host_proof:{path,sha256}`. First independently verify the actual executor and all writable descendants stopped. The private proof JSON binds `version:1`, `kind:"check-writer-reconciliation"`, task `identity`, `expected_pins`, current `expected_revision`, `scope_id`, `attempt_id`, original `candidate_digest`, `current_candidate_digest`, `plan_digest`, `execution_digest`, `stopped:true`, `descendants_stopped:true`, `observation_ref` and `coordinator_ref`. Use public task/attempt results and fresh evidence status for these bindings. A crash without a durable execution result uses null `execution_digest` and cannot become passing evidence. Retain the underlying host observation; booleans or references alone do not establish authority. Reconciliation preserves actual failed/timed-out results and requires unchanged inputs before promoting observed success.

`evidence review prepare` requires `coverage` (nonempty subset of `general`, `security`, `behavior`), covered criterion IDs, and exact read-only reviewer `assignment` (1–65,536 characters). It returns `attempt_id` and `task_name`; use that exact `review_<attempt_id>` name for the native delegation. `collect` then requires that attempt plus native `parent_turn_id` and `spawn_item_id`; it fetches the receipt and report itself. `assess` requires the same `attempt_id` and an `assessment` with covered `coverage` and `criteria`, coordinator `qualification`, `independence`, `semantic_coverage`, finding `dispositions` (`finding_id`, `status` resolved/accepted/open, reference), and `decision_refs`. Optional `rechecked_findings` binds a fresh review attempt and finding ID to resolved/open status and reference. High/critical confirmed security findings cannot be accepted.

`evidence verify` requires purpose `completion` or `merge-evidence`; optional `reuse` entries need an attempt ID, reason, and unchanged relative dependencies. Optional current `security_impact` (`status`, `reason`, `reference`) is required after candidate changes unless a new plan recaptures that candidate; unresolved impact blocks. `status` takes `--client codex --session SESSION` and recaptures readiness.

`task retire` uses the common identity plus `expected_pins` (`schema_version`, `policy_digest`, `runtime_digest`), reason, reference, and `stop_proof` absolute private path/SHA-256. The proof file (JSON, at most 128 KiB) has `version:1`, `kind:"stopped-writer-reconciliation"`, exact `identity`, `expected_revision`, `expected_pins`, `observed_turn_id`, `stopped:true`, `descendants_stopped:true`, ordered `attempt_ids`, `observation_ref`, and `coordinator_ref`. Retirement only cancels and preserves history; if authority or writer state cannot be verified, the task remains blocked. An interrupted `reserved`, `running`, or `uncertain` attempt blocks readiness and plan changes; do not treat a retry as clearing that record. Resolve uncertainty through observed reconciliation, or retire only with the required trusted proof.

## Completion and limits

Use `verify` with purpose `completion` before claiming the task complete; use `merge-evidence` to check local evidence before a merge. Merge evidence always requires general review and applicable security review, including for trivial changes. Only successful completion verification can set `ready`; ordinary task updates cannot set it. Verification rechecks current content and blockers. A changed candidate, plan, relevant environment, policy, or check invalidates affected proof. Reuse unaffected evidence only with a recorded reason and unchanged dependencies.

Missing, stale, failed, interrupted, ambiguous, or unverified proof blocks dependent completion. Confirmed high/critical security findings block; medium/low findings need resolution or authorized disposition. A readiness result is point-in-time local evidence, not merge authorization or proof that a repository gate passed. D7 repository enforcement remains separate. Hooks and generation are invalidation hints, not a security boundary or proof of unchanged content.

When changing the pinned runtime, stop and reconcile affected writers before retiring historical tasks. `task retire` requires exact stored identity, revision and pins plus a private digest-checked stopped-writer reconciliation proof; the coordinator must verify its authority. It preserves original pins and history and cannot make a task ready. Do not silently repin tasks, copy evidence, or delete old state. If required reconciliation cannot be observed, leave the upgrade blocked.

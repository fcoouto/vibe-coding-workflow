# Task checks and review evidence

Load this contract for a Codex task that needs accepted checks, general or security review, a completion decision, or local merge evidence. Follow the full [Tests and Builds](../policies/05-tests-and-builds.md), [Code Review](../policies/06-code-review.md), and [Security Review](../policies/04-security-review.md) contracts; this file gives the local controls, not replacements for those policies. This is task runtime guidance: do not load Toolkit sources, setup/onboarding procedures, or Superset guidance. Load [native delegation](delegation.md) only for native review preparation, lifecycle observation or recovery. Direct checks need no D6 native plan, discovery, model choice or guidance.

## Plan and capture

Use the installed package's `scripts/workflow.py` with the enrolled checkout as `--cwd`. Mutations take the current Codex client/session/task/scope identity and `expected_revision` as bounded JSON on stdin. Start and update controls remain in [task runtime](runtime.md). Evidence operations are:

```sh
python3 -I -B /path/to/package/scripts/workflow.py evidence plan --cwd /checkout < plan.json
python3 -I -B /path/to/package/scripts/workflow.py evidence status --cwd /checkout --client codex --session SESSION
python3 -I -B /path/to/package/scripts/workflow.py evidence check --cwd /checkout < check.json
python3 -I -B /path/to/package/scripts/workflow.py evidence reconcile-check --cwd /checkout < reconciliation.json
python3 -I -B /path/to/package/scripts/workflow.py evidence review prepare --cwd /checkout < prepare.json
python3 -I -B /path/to/package/scripts/workflow.py evidence review collect --cwd /checkout < collect.json
python3 -I -B /path/to/package/scripts/workflow.py evidence review assess --cwd /checkout < assess.json
python3 -I -B /path/to/package/scripts/workflow.py evidence verify --cwd /checkout < verify.json
```

The plan records acceptance criteria, accepted command definitions and thresholds, execution limits, baseline, candidate/base comparison, exclusions, and risk-based review applicability. Preserve `required`, justified `inapplicable`, or `unresolved` for each review scope; lack of a tool or reviewer is unresolved. Every completed change needs an assessed security impact. Do not invent commands or treat request JSON as permission to change thresholds or authorize side effects. Use existing decision references for accepted rules; a changed rule needs the established decision process.

Checks run only the planned argv and environment, without shell interpretation or inherited credentials. Checks and native reviews share participating resource ownership under the [approved state authority](runtime.md#opt-in). Review collection verifies the prepared task marker in native parent/child records, child checkout, completed turn, and fetched final report. The native prompt is encrypted and is not claimed as observed; receipt proves execution identity, not review quality or read-only enforcement. The coordinator must check semantic coverage and findings against the target. Keep detailed snapshots, output, and reports in the private evidence area; records contain bounded summaries and digests, never raw transcripts or secrets.

Review collection selects `codex` from the command's `PATH` and requires the observer, parent and reviewer native versions to match a qualified version. For Desktop, prefix only the collection command's `PATH` with the matching bundled executable's directory. Preserve global settings and `PATH`. Unavailable or mismatched versions leave independent review unverified.

## Request fields

Every mutation JSON object includes `client:"codex"`, `session_id`, `task_id`, `scope_ref`, and current positive `expected_revision`. Use the revision returned by the previous operation; after a conflict, read status and prepare a fresh request. JSON input is limited to 128 KiB; unknown fields reject.

`evidence plan` takes `plan` with version 1 and these required fields: `decision_ref`; `criteria` (`id`, `checks` command IDs, `behavior` boolean); `checks` (`id`, exact `argv`, relative `cwd`, `timeout` 1–300 seconds, explicit credential-free `env` containing `PATH` and optionally `LANG`, `LC_ALL`, `TZ`; `effects` with `kind` read-only/disposable, `inspection_ref`, and `network`, `production`, `publish`, `migrations` all false; `baseline` status passed/failed/not-run and reference; relative `dependencies`); `reviews` for `general` and `security` with `applicability` required/inapplicable/unresolved, reason, and independent boolean; `security_impact` status assessed/unresolved, reason, reference; `base`, `comparison` endpoint/merge-base, `nontrivial`, absolute safe `instructions`, relative `exclusions` with impact, and `review_limit` 1–8. There must be 1–32 criteria; checks may be empty only when behavior is observed, otherwise include up to 32 accepted commands. Optional `relevant_untracked` lists relevant ignored paths; optional check `thresholds` can only be `{"exit_codes":[0]}`. Mutable/disposable checks require declared `resources` using `_claims` in [runtime/delegation.py](../runtime/delegation.py). Genuinely read-only checks may derive read claims from declared dependencies; an empty or unknown footprint serializes affected checkout work. Never infer mutable-resource isolation. A comparable failed baseline may include its integer `exit_code` and SHA-256 `output_digest`; only an exact signature match is pre-existing, otherwise failure comparison remains unresolved. Changing accepted rules requires `change_decision_ref`.

`evidence check` requires `check_id` and accepts a stable `dispatch_id`. It atomically reserves one check attempt and same-ID ownership row before running that exact planned command. Replay returns stored state without rerunning the command. Without an explicit dispatch ID, identity derives from check ID and original request revision; retain that request for replay. An unresolved exact check cannot run again. Check attempts retain D5 limits and consume no native attempt/resource units. Output is private, bounded to 128 KiB, and common credential lines are redacted. Observed outcomes remain pending lifecycle reconciliation: a parent exit or empty process group cannot prove detached descendants stopped. A failed check can be retried after its lifecycle is reconciled and its result addressed or understood; introduced failures block. Changed inputs, timeout, overflow, or uncertain surviving processes do not pass.

`evidence reconcile-check` requires `attempt_id` and `host_proof:{path,sha256}`. First independently verify the actual executor and all writable descendants stopped. The private proof JSON binds `kind:"check-writer-reconciliation"`, task `identity`, `expected_pins`, current `expected_revision`, `scope_id`, `attempt_id`, original `candidate_digest`, `current_candidate_digest`, `plan_digest`, `execution_digest`, `stopped:true`, `descendants_stopped:true`, `observation_ref` and `coordinator_ref`. Linked schema-2 checks require proof `version:2` and exact `dispatch_id`, `assignment_digest` from the attempt's `ledger_assignment_digest`, and `claims_digest` from its `ledger_claims_digest`. `_validate_operation_proof` defines this check variant. Historical unlinked version-1 proofs retain their original meaning; follow their supported pinned-runtime reconciliation rather than inventing ledger/native bindings or adopting old success as fresh proof. Use public task/attempt results and fresh evidence status for these bindings. A crash without a durable execution result uses null `execution_digest` and cannot become passing evidence. Retain the underlying host observation; booleans or references alone do not establish authority. Reconciliation settles the exact check attempt and ownership row together. It preserves actual failed/timed-out results and requires unchanged inputs before promoting observed success. Recapture proof after intervening candidate, ownership or observation changes.

`evidence review prepare` is the sole native review admission entrypoint. It requires an accepted D6 plan with a read-only `review` job; `coverage` (nonempty subset of `general`, `security`, `behavior`), covered criterion IDs and exact plain reviewer `assignment` (1–65,536 characters); plus explicit `dispatch_id`, `job_id`, `selection`, `control_observation`, `discovery_expectation`, `guidance` and `resource_units`. Optional `retry_of`/`diagnostic` retain bounded retry semantics. Use `prepare_review` in [runtime/evidence.py](../runtime/evidence.py) and the [native preparation procedure](delegation.md#prepare-and-launch-once). Nothing selects these inputs automatically.

Preparation atomically creates one shared attempt/ownership UUID, consumes one D5 review round and native admission, and returns the exact `review_<attempt_id>` marker, prompt, `requested_model`/`requested_effort` and once-only launch permit. Follow delegation's single-launch procedure; worker preparation cannot admit a reviewer. Fixes, retries and a new plan cannot reset original round or admission limits. D5 `assignment_digest` remains SHA-256 of the exact plain assignment; `ledger_assignment_digest` separately identifies the D6 immutable ownership/selection artifact. Version-1 review reports/receipts retain the D5 meaning. Version-2 lifecycle observation binds the D6 digest; never substitute one for the other. Legacy v1 `requested_*` receipt fields describe spawn-observed settings, not modern requested settings.

Use `delegation observe` for the same prepared reviewer and actual parent-turn/start-item identity before quality collection. It can record incomplete or mutated work without accepting review quality. `evidence review collect` requires that attempt plus native `parent_turn_id` and `spawn_item_id`; it fetches the completed/current-candidate receipt and report, then correlates the same child, start, turn, result item and raw-result digest with lifecycle observation. A mismatch, invalid report or changed candidate cannot pass. First collection requires the D5 attempt to remain `reserved`; no same-attempt recollection API exists. Collection and assessment neither launch another reviewer nor release ownership. A valid report may be assessed while stopped-descendant proof remains unresolved; complete exact reconciliation through [native recovery](delegation.md#observe-and-reconcile-independently). `assess` requires the same `attempt_id` and an `assessment` with covered `coverage` and `criteria`, coordinator `qualification`, `independence`, `semantic_coverage`, finding `dispositions` (`finding_id`, `status` resolved/accepted/open, reference), and `decision_refs`. Optional `rechecked_findings` binds a fresh review attempt and finding ID to resolved/open status and reference. High/critical confirmed security findings cannot be accepted.

Assessment, completed ownership reconciliation and positive completion evidence must still match the latest uncontradicted completed lifecycle result. A later failed, interrupted, malformed or different result supersedes older quality without erasing historical findings or dispositions. If an assessed review becomes superseded, reconcile its exact ownership as failed/cancelled, then prepare a fresh explicit review within the original limits. A matching later turn may be collected before first collection. Resolving a historical finding requires fresh scoped assessment; a new clean report alone does not resolve it.

`evidence verify` requires purpose `completion` or `merge-evidence`; optional `reuse` entries need an attempt ID, reason, and unchanged relative dependencies. Optional current `security_impact` (`status`, `reason`, `reference`) is required after candidate changes unless a new plan recaptures that candidate; unresolved impact blocks. `status` takes `--client codex --session SESSION` and recaptures readiness.

`task retire` uses the common identity plus `expected_pins` (`schema_version`, `policy_digest`, `runtime_digest`), reason, reference, and `stop_proof` absolute private path/SHA-256. The proof file (JSON, at most 128 KiB) has `version:1`, `kind:"stopped-writer-reconciliation"`, exact `identity`, `expected_revision`, `expected_pins`, `observed_turn_id`, `stopped:true`, `descendants_stopped:true`, ordered `attempt_ids`, `observation_ref`, and `coordinator_ref`. Retirement only cancels and preserves history; it cannot clear unresolved shared assignments. Reconcile each exact assignment first, including retained history and other relevant sessions/scopes. If authority or writer state cannot be verified, the task remains blocked. An interrupted `reserved`, `running`, or `uncertain` attempt blocks readiness and plan changes; do not treat a retry as clearing that record. Resolve uncertainty through exact observed reconciliation before retirement; the retirement proof does not replace assignment or check reconciliation.

## Completion and limits

Use `verify` with purpose `completion` before claiming the task complete; use `merge-evidence` to check local evidence before a merge. Merge evidence always requires general review and applicable security review, including for trivial changes. Only successful completion verification can set `ready`; ordinary task updates cannot set it. Verification first reserves its own read-only resource barrier, then rechecks current content and blockers across relevant sessions/scopes/history. Only its own completed synchronous barrier settles automatically with the result; other relevant claims remain blockers. Successful completion releases that barrier and records `ready` atomically. A later conflicting reservation invalidates affected readiness in the same admission transaction. A changed candidate, plan, relevant environment, policy, or check invalidates affected proof. Reuse unaffected evidence only with a recorded reason and unchanged dependencies.

Missing, stale, failed, interrupted, ambiguous, or unverified proof blocks dependent completion. Confirmed high/critical security findings block; medium/low findings need resolution or authorized disposition. A readiness result is point-in-time local evidence, not merge authorization or proof that a repository gate passed. For repository merge assurance only, read [repository merge assurance](repository-gate.md). Its bounded fixture inspector always exits 1; production sources, publishing and enforcement remain unqualified. Hooks and generation are invalidation hints, not a security boundary or proof of unchanged content.

For an authorized runtime update or recovery, follow [the fresh-state transition](runtime.md#change-a-pinned-runtime). Keep the retirement and exact assignment proof boundaries above; changing state authority cannot clear unresolved ownership.

## Internal canonical schema-3 evidence

Read this section only when changing or auditing canonical evidence storage, or handling linked plan-v2 completion/status; its runtime activation boundary is in [task runtime](runtime.md#internal-canonical-schema-3). Under an internal accepted schema-3 scope, artifact registration uses a scoped transaction and metadata that binds the artifact owner, digest, byte count, managed file identity/mode, parent-directory identities, dependencies and targets. Task artifacts remain bound to the exact accepted task and physical checkout.

Fresh schema-3 authority creation may add a compact `authority-source-baseline` containing the authority identity, original creation time and runtime digest. Historical `source_contract:1` records this bootstrap provenance only and is not retrofitted. `source_contract:2` is created under the D4 registration protocol, which requires validation of the admission and final-source-hook sources, edges and authorities; those event/source receipts are not contents of the baseline itself. Neither version is a complete source inventory, proof of full lifecycle completeness, membership proof, physical evidence cleanup/expiry implementation, or aggregate verification.

Private owner-only `evidence.close_task` supports one existing `source_contract:2` schema-3 authority. For an already-cancelled task, it requires exact retained coordinator-stop proof and complete, independently reconciled coordinator/check/worker/review assignments with matching D4 certificates, including explicit not-started proofs. For an ordinary ready task, it requires an actual independent complete-task stop proof while preserving the original ready revision, pins and age; the synchronous-verifier barrier remains historical proof and cannot be treated as a fresh stop. Missing, uncertain, changed, or unknown owners block closure; a cancelled task with only a legacy version-1 stop and synchronous-verifier barrier remains unsupported. The compact record retains original source refs and ages, numerical check facts, findings/dispositions, worker provenance, stop/reconciliation certificates, and native plus current/historical scope-guidance sources; native usage remains unknown. Historical guidance can continue through exact source proof, but a failed changed-applicability refresh never authorizes new dispatch. Closure preserves the original cancelled or ready state, revision, pins and age; ready closure remains historical and grants no fresh implementation, merge, or delivery authority, while cancellation creates no implementation or delivery success. Assignment markers precede assignment-row removal, then exact task/turn/receipt markers precede their row removal; evidence files remain. Linked/foreign-owner closure, temporary review-owner accounting, physical deletion/expiry/caps/4096 reclamation, and public canonical routes remain unsupported. These internal calls do not qualify native execution or expose a public CLI.

The internal linked evidence-plan version 2 has `linked:{acceptance:[{id,text}],delivery:null|{provider,repository,target,pull_request},companions:[{task,delivery}]}`. Validation checks this listed shape and participant projection; it does not establish that the companion set is complete. Ordinary `verify` still blocks version-2 linked plans. The internal `verify_linked` path can record aggregate verification only when its trusted coordinator caller supplies independently checked current scope and complete participant observations, matching normalized plans, each member's current local proof, and supported shared-criterion/source evidence. A callback, private Python bundle, JSON, retained reference, or digest alone does not authenticate authority or completeness.

The aggregate pointer and readiness change are written only to the selected task. Member preparation may record each peer's ordinary local verification; linked publication does not modify peer rows or publish aggregate pointers there. `implementation_verified` and `delivery_complete` are separate: passing implementation proof does not establish required delivery, and an open or unknown delivery does not by itself invalidate implementation. Linked status rechecks the complete stored member set, current rows/generations and retained sources even when it cannot change readiness; stale or unavailable support is not passing evidence. This internal path is not exposed by the public task evidence CLI, does not enable public canonical activation or native qualification, and never grants merge authority.

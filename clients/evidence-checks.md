# Checks and reconciliation

Apply the [common evidence contract](evidence.md) before this procedure.

Ordinary checks require qualified applicable capabilities. A [qualification task](runtime.md#staged-qualification) may execute only its retained approved operation, within the original attempt allocations and deadline. Its effective command timeout cannot exceed that remaining deadline; replay and successor receipts do not renew execution permission. Exact lifecycle reconciliation remains available after execution permission ends.

`evidence check` requires `check_id` and accepts a stable `dispatch_id`. It atomically reserves one check attempt and same-ID ownership row before running that exact planned command. Replay returns stored state without rerunning the command. Without an explicit dispatch ID, identity derives from check ID and original request revision; retain that request for replay. An unresolved exact check cannot run again. Check attempts retain D5 limits and consume no native attempt/resource units. Output is private, bounded to 128 KiB, and common credential lines are redacted. A durably recorded executor launch failure settles automatically as failed: no process was started. Other observed outcomes remain pending lifecycle reconciliation: a parent exit or empty process group cannot prove detached descendants stopped. A failed check can be retried after its lifecycle is reconciled and its result addressed or understood; introduced failures block. Changed inputs, timeout, overflow, or uncertain surviving processes do not pass.

If a D6 plan contains a matching `check` job, the check must satisfy that job's dependencies before reservation or execution. Read-only checks may follow a compatible same-task cooperative worker. Checks without a matching D6 job retain their ordinary D5 admission rules. This does not change check reconciliation.

`evidence reconcile-check` requires `attempt_id` and `host_proof:{path,sha256}`. First independently verify the actual executor and all writable descendants stopped. The private proof JSON binds `kind:"check-writer-reconciliation"`, task `identity`, `expected_pins`, current `expected_revision`, `scope_id`, `attempt_id`, original `candidate_digest`, `current_candidate_digest`, `plan_digest`, `execution_digest`, `stopped:true`, `descendants_stopped:true`, `observation_ref` and `coordinator_ref`. Linked checks require proof `version:2` and exact `dispatch_id`, `assignment_digest` from the attempt's `ledger_assignment_digest`, and `claims_digest` from its `ledger_claims_digest`. The [complete role proof fields](delegation-proofs.md#check) define this check variant. Historical unlinked version-1 proofs retain their original meaning; follow their supported pinned-runtime reconciliation rather than inventing ledger/native bindings or adopting old success as fresh proof. Use public task/attempt results and fresh evidence status for these bindings. A crash without a durable execution result uses null `execution_digest` and cannot become passing evidence. Retain the underlying host observation; booleans or references alone do not establish authority. Reconciliation settles the exact check attempt and ownership row together. It preserves actual failed/timed-out results and requires unchanged inputs before promoting observed success. Recapture proof after intervening candidate, ownership or observation changes.

Omit `host_proof` only when the retained executor receipt explicitly records that
no process started. The runtime derives exact bindings from that receipt; it
cannot turn this failure into passing evidence. A started command still requires
independent host reconciliation, including a declared read-only command.

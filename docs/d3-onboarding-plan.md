## Private plan and interfaces

Use a caller-selected absolute `--plan-dir`, canonical and private to the current user, outside target repositories, plugin caches and client instruction/skill discovery paths. Reject links and special files. Do not silently choose a vendor's plugin-data directory or provision the eventual shared runtime state directory. Store one versioned `plan.json`, bounded source material and sanitized evidence references there. Serialize each plan read/check/replace under a short, bounded per-plan OS advisory lock on the currently qualified POSIX filesystem; atomically replace in the same directory while holding it. Fail busy without a retry loop. Never hold the lock across source retrieval, agent work or checks. This is not D4's apply journal; no database is needed. Bound reads and source/plan sizes; exceeding a limit produces an explicit incomplete result, never silently partial coverage.

Implemented dispatcher commands:

| Command | Responsibility |
| --- | --- |
| `onboard inspect --cwd PATH --plan-dir PATH` | Read bounded source metadata from stdin, resolve target identity and record deterministic inventory. For an existing run, verify its pinned scope/inputs and report changes; never overwrite it as a new run. No network or project command execution. |
| `onboard plan --plan-dir PATH` | Read a bounded semantic proposal from stdin; validate expected plan revision and current pins, replace agent-authored decisions/coverage/actions/evidence and return current status. Preserve decision dispositions and invalidation history. |

Implemented `inspect_project(cwd, plan_dir, source_record)` and `record_plan(plan_dir, request)` in `runtime/onboarding.py`. Resume uses the same inspect/plan commands; there is no separate resume engine or status command. Requests use strict JSON with explicit limits rather than increasing the hook's 128-KiB limit. Reports include `plan_id`, revision, `draft|awaiting_decision|blocked|ready_for_review|stale`, blockers, next decision and evidence limits. Exit `0` means ready for review; `1` means invalid/unsafe input, busy lock or revision conflict; `2` means draft, awaiting decision, blocked or stale. A plan status does not mean enrollment or approval. Helpers never prompt interactively.

## Source and target rules

**New run:** the agent resolves Toolkit `main` once through the canonical upstream using available connector/tool capabilities, records the returned commit and retrieves required sources at that commit outside the target. Record source references, retrieval observations and path/content hashes in the private plan. Keep only required temporary material; no standalone downloader is needed. Deterministic helpers validate declared metadata/hashes and cannot authenticate upstream ownership from a record alone. Source retrieval is bounded and never uses the target checkout as a work directory. Discover the complete catalog from the pinned overview/catalog, not the plugin's eleven policies or a hard-coded list of previously known tools. Resolve referenced guides/templates needed for applicability before treating their rows as assessed. Missing required source blocks dependent assessment only.

**Offline input:** the agent may supply an explicitly trusted, versioned copy whose commit identity and required-file hashes can be recorded. Missing trust/provenance stays pending; a directory name or claimed JSON revision does not prove it. Report freshness unverified and retain dependent gaps. Do not silently treat the previously reviewed policy revision as current upstream.

**Resume:** inspect/plan retain the run's pinned revision; do not resolve main again or upgrade the source pin. If retained source files are missing, retrieve only that commit when authorized or use a trusted matching copy. Changed source bytes stale dependent coverage and cannot be reconciled to new bytes. A requested upstream refresh starts a new run; carry forward only decisions whose evidence still applies.

**Current implementation targets:** legacy input resolves one selected Git checkout with inherited Git selectors removed; a non-Git legacy destination remains a prerequisite, never `git init`. Explicit Project input supports bounded standalone/umbrella private inspection and scoped proposals with the selected checkout as each Repository's action base. Primary/common-Git resolution locates membership/guides; initial duplicate common-Git selections and uncertain authority/bindings remain blocked. It does not adopt members, extend startup or authorize live rollout. Broader rollout still follows the qualified pilot.

Read bounded regular files only; record symlink/unreadable/oversized/excluded paths and their assessment gaps. Inventory instructions applicable from ancestors through the selected paths without expanding edit authority outside selected scope. Recheck checkout identity, relevant content/absence fingerprints, source and installed-policy/runtime pins before accepting a revision as current. Track staged/index changes, unstaged and relevant untracked content; HEAD alone is insufficient. A same-run reinspection reports `current_input_digest`; a plan request can reconcile reviewed current checkout/package changes using that exact digest and a reason. Reconciliation retains invalidation/decision history, preserves unrelated choices and revalidates the full proposal. It cannot change checkout identity or accept changed pinned source bytes. D4 repeats these checks immediately before apply.

## Agent judgement and deterministic checks

The agent reads product/instruction context, establishes catalog semantics, classifies need and equivalents, identifies semantic conflicts, chooses safe baseline commands, assesses merge feasibility and drafts exact actions. Helpers enumerate bounded metadata, hash inputs, enforce schema/identity/revision consistency and validate explicit catalog IDs, dependency references, unresolved decisions and evidence references. They cannot prove semantic completeness, equivalence, safe arbitrary shell commands or absence of conflicts. `ready_for_review` requires the agent's explicit scoped semantic assessment plus passing structural checks; report both separately.

Run available safe baseline checks after inspecting what the command actually does. The helper is not an arbitrary command runner. Metadata reads use read-only Git behavior with optional locks disabled. Project commands must be demonstrated to leave target/client/account state unchanged; redirect disposable caches/output outside the target. Otherwise run against an explicitly identified disposable snapshot reflecting current relevant content, record that evidence scope, or record `not_run` with the exact prerequisite. No installs, service startup, external mutations or paid evaluation merely to obtain a baseline. Capture command, candidate/input fingerprint, environment facts needed for interpretation, exit/outcome and pre-existing failures; do not equate an exit code with enrollment qualification.

Ask one focused question only when a missing material decision affects scope, behavior, access, cost, architecture or enforcement. Reuse valid inherited choices with their evidence. No conflict means no mode question. In noninteractive operation, return the pending question, affected actions and resumption condition; continue independent read-only assessment. An unanswered recommendation remains pending.

Apply all three conflict modes from policy 01. Required adoption is never optional: preserve mode retains conflicting behavior and blocks dependent adoption; replace mode proposes retirement of the whole approved legacy workflow layer, including compatible process rules, while preserving product rules and stated exceptions. Mixed files use one full-postimage action per file; the section field describes the authorized area and does not splice content. Shared/global integrations remain separately scoped. Every optional omission has a reason; a runtime action's justified inapplicability never removes mandatory policy adoption. An equivalent needs observed behavioral evidence or remains unqualified. Merge feasibility records actual host/trust/access constraints and a D7 dependency rather than proposing unauthorized live rule changes. The coverage plan includes the required native harness evaluation method and initial smoke cases; optional CLI labs and paid experiments remain separate choices.

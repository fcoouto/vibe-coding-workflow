# Workflow simplification, first round

The user approved all ten recommendations from the whole-project audit on 2 November 2026. This is the implementation scope, not a new approval gate. The objective is a useful plug-and-play workflow whose controls protect concrete feature requirements and actual effects.

## Approach

Use the existing SQLite authority, transaction journal, native tools and local policy contracts. Delete unrelated admission dependencies, consolidate repeated observations and load detailed procedures only for their triggering operation. A new framework, signer, registry, service, blanket bypass or rewritten historical authority would work against the requested outcome.

Keep the primary checkout and other chats' candidates untouched. Start from merged PR30 (`e3128c6`), retain its file-recovery fix, and do not install, onboard, merge, or operate live runtime stores as part of source implementation. Native execution remains separately qualified.

## Approved outcomes

1. A valid configured-only canonical checkout permits ordinary work without claiming managed activation. Explicit task/evidence/delegation controls still require active accepted scope. Conflicting identities and unknown active ownership remain protected.
2. Preserve the merged file-configuration/undo protections. Evaluate recovery eligibility from changed effects and affected members, rather than unrelated active members. Do not simplify a change to active/shared dependencies into file-only recovery.
3. Keep original source fingerprints as provenance. Supported schema and relevant accepted behavior determine compatibility; unrelated package bytes must not require reenrollment. Historical task identities and accepted policy stay unchanged. Incompatible records remain rejected by their existing readers.
4. Use executor-owned check receipts. Eliminate separate coordinator-authored stop proof where the actual operation establishes completion without uncertain writable descendants. Arbitrary writable or detached commands retain reconciliation. Declaring a command read-only is not OS containment.
5. Retain one authoritative fact and direct dependencies. Consolidate repeated publication/closure observations within a guarded stage and separate cleanup from unrelated publication work. Preserve historical readers, crash recovery, permission checks and exact retention semantics.
6. Admission inspects relevant current ownership and exact referenced historical results. Settled unrelated history does not consume a live-admission limit. Keep bounded parsing and scans, replay protection and relevant uncertain writers.
7. Sequential heavy phases reuse their assignment's capacity reservation without double-charging, while uncertain or simultaneous workloads retain occupancy. Feature preferences and phase replay protection remain independent.
8. Derive deterministic onboarding hashes and bindings from existing observations. The coordinator supplies semantic decisions and intended effects. Full required catalog coverage, current setup sources and exact approved changes remain intact.
9. Keep purpose and essential rules in short entry points; load dispatch, evidence, recovery and merge procedures only when needed. Preserve every actual requirement and source-to-contract coverage. Routine requests must not require reading implementation internals.
10. Reuse acquired startup scope and skip unchanged title synchronization. Relevant state changes, pending repair and explicit refresh still reconcile titles, including user edits. Presentation failure never alters task authority.

## Completion and risk

Use focused failing regressions before behavior changes, existing tests for preserved invariants, package validation and a final independent review. Exercise configuration, a small direct edit, a check, delegated work, interruption and undo using disposable fixtures. Report package proof separately from native execution. Review requests must keep the coordinator's Astra/high model, provider, authentication and permissions unchanged; no alternative model route is authorized by this design.

Do not label a feature complete by merely changing its documentation or suppressing a failure. If a proposed deletion cannot preserve the actual safety requirement, retain the necessary protection, record the precise boundary, and implement the smaller supported simplification. Further rounds follow demonstrated user friction, not a percentage target or endless audits.

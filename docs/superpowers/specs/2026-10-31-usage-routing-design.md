# Usage Routing: direct OpenAI credits pilot

Design revised on 3 November 2026 after Astra's review and the user's decision to keep Smart Balance in the first release. The user accepted the matching grant row's expiration date, the Codex connector and dashboard observation workflow, and the three ceiling choices below. The first version uses one runner, one shared ledger and conservative admission. Best-effort grant use requires warnings and early native handoff. Auto-reload OFF and provider funding isolation are optional. Local budget enforcement cannot guarantee account-wide funding isolation. See the [validation record](../../usage-routing-validation.md) for implementation and authorized pilot results.

Store the API credential in **macOS Keychain**. Plaintext env-file storage is excluded. The earlier env-file setup stopped after three destination confirmation calls returned a decline without a visible form, as reported by the user. Those attempts created no key.

## Purpose and name

Reduce ChatGPT/Codex subscription consumption per accepted task without weakening quality, independent review, permissions, or access to other providers.

Call the feature **Usage Routing**, with modes **Off**, **Manual**, and **Smart Balance**. Off is the default. Its funding policy is **API credits only**, initially supporting direct OpenAI API calls. Use one management skill, `manage-usage-routing`, displayed as **Manage Usage Routing**. Keep OpenRouter's existing management and consent intact; do not rename or migrate it in this slice. Avoid names promising automatic savings or implying that every API request is free.

Treat credits as a user-authorized existing funding pool, regardless of whether they were granted or purchased. Do not market the feature as subscription-benefit-only. The plugin never initiates purchases/recharge or deliberately switches an API task into another paid funding pool. Account-side auto-reload or funding spill may still occur; warn without requiring a billing change or funding-isolation guarantee. Prefer the selected subscription grant and stop API work conservatively when coverage becomes doubtful. Protect interactive subscription capacity and required independent review by default; this is not an optional setting.

## Current delivery: Manual and Smart Balance

Use one coordinator-owned direct API runner and one durable local ledger shared by participating Codex sessions. Allow one active API request at a time across those sessions, reserve its maximum cost before sending, and pause whenever funding, expiry, pricing or the outcome is uncertain. During initial validation, keep only one original API task outstanding through native integration and independent review; releasing the API slot alone does not admit another task. All three monthly ceiling choices use the same admission rule. Independent native review and existing provider routes remain unchanged.

Smart Balance is required in this delivery, alongside Manual; it is not a later feature or optional follow-up. Build and offline-test its selector now with the shared controls, observation handoff, native-capacity protection and review integration it depends on. A small bounded evaluation qualifies the first task class/profile and its capacity evidence within this same delivery. Default remains OFF. Local feature enablement may be saved with the funding warning even while live dispatch is unavailable; actual requests still require consent, valid credit coverage, a working authenticated adapter, quality and native capacity. Auto-reload status does not determine enablement. A dependency blocker leaves Smart Balance implemented/testable in shadow mode with a specific reason; it does not remove Smart Balance from scope or authorize unsafe activation.

Keep demand forecasting, adaptive allocation, savings-per-dollar ranking, automatic model escalation, multi-request concurrency and broader client support out of this version. Smart Balance chooses only already-qualified work using a short deterministic policy. It does not run an LLM router, monitoring agent or idle polling schedule. Expiry may prioritize useful ready work of equal user priority; it never creates work or expands a budget.

## Evidence and limits

The current checkout implements native delegation, OpenRouter text proposals and pinned OpenCode read-only workers. The OpenCode runner hardcodes OpenRouter, delegates retry ownership to OpenCode, and reports costs that are not independently reconciled billing. Native review evidence remains authoritative. Langfuse configuration is not a workflow usage collector.

Official documentation checked on 31 October 2026 establishes that the subscription grant applies to eligible calls billed to the linked organization, excludes Codex API-key usage, and can spill into purchased credits. Platform hard limits have enforcement delay. Subsequent read-only evaluation observed native Codex weekly usage and reset information, billing-page grant details, and connector benefit expiry. This does not establish a supported grant-balance API or per-request promotional-only flag. Account-side funding prevention and direct-route attribution remain unverified.

### Accepted expiry source: Codex only

Use the OpenAI Developers connector's read-only `preview_api_credit_promo` as the expiry source in Codex. Inspection of installed version 1.3.13 and a live Codex call confirmed that an already-linked account can return `benefit` with `cadence`, `currency`, `period_credit_amount_usd`, and an exact UTC `expires_at`, even when `eligible` is false, `ineligibility_reason` is `already_linked`, and `offer` is null. Those eligibility fields describe whether a new claim is available; they do not invalidate an otherwise valid current benefit. The connector explicitly does not confirm grant delivery. Period credit is not remaining balance.

Use the host-managed ChatGPT authentication declared by the connector. Do not copy session credentials or implement a standalone client for its internal endpoint. Bind observations to the observed account/workspace and separately verified linked organization; the preview response alone supplies no organization identifier. Record source/version and observation time, preserve the timestamp's timezone, and invalidate observations after account/workspace changes. A missing, expired, stale, malformed, or contradictory benefit blocks expiry-dependent admission. Renewal triggers a refresh, not an assumed new balance or grant.

Accept the matching Credit Grants row's displayed expiration date for the selected pool; no additional grant identifier is required by this design. Use the connector's exact UTC expiry when it agrees with that row and account binding. If only a date is available, stop before that date begins in the established billing timezone; if the timezone is unknown, use the earliest plausible start of that date. This is a conservative local cutoff, not proof of the provider's funding attribution. Do not assign this expiry to other balances or treat a date match as proof of settlement.

Qualification is limited to live, read-only Codex access. Unattended Codex invocation, authentication refresh/recovery, and renewal transitions remain validation work. Standalone Vibe access remains unverified and outside this qualification. No schedule is created by accepting this source. Remaining balance and grant delivery require their own usable observations; the connector does not prove provider funding isolation, which is a warned risk rather than an enablement requirement.

### Monitoring cost and refresh policy

Use one private, organization-bound observation cache alongside the existing proposed ledger, shared by participating Codex sessions. Keep account/workspace identity, independently verified organization binding, currency, observed balance, grant coverage when known, source/version, timestamps, and validity reason. Reuse existing runtime storage and bounded evidence patterns; do not add another model, agent, dashboard, daemon, database, or generic provider framework for monitoring.

1. When routing is off or no API work is pending, do not poll or wake a model. Cached status remains a local read with its age and limitations.
2. At an eligible task boundary, use the fresh shared observation and deterministic reservations. Refresh once if required by freshness, renewal, account change, unexplained balance movement, or headroom insufficient for the next bounded request. Coalesce simultaneous refresh requests per organization.
3. Retain the pilot's proposed 15-minute maximum balance-evidence age at admission, subject to qualification; this is not a 15-minute polling schedule or protection against external spending. A failed refresh does not extend freshness. Do not remove usable grant coverage, maximum-cost bounds or retained reservations merely to reduce monitoring cost.
4. Between observations, use integer arithmetic and durable reservations, not model reasoning or a provider read before every tool call. Native coordinator tokens still pay for invoking UI tools; a scripted locator sequence is not automatically a zero-token background service.
5. Return only a compact status tuple to routine context: route state, authorized headroom, observation age, expiry and reason. Load discovery/setup procedures only for setup, expired evidence or failures. Store full financial evidence privately, not in prompts or repository history.
6. Bound each on-demand refresh attempt. On unavailable controls or authentication, stop, preserve uncertainty and pause affected admissions once evidence is invalid. Automated surface/authentication repair is outside this delivery. Avoid repeated repair conversations or silent switches to another funding source.

Measure monitoring input/output tokens, native allowance where observable, tool calls, latency and recovery work separately. Include these plus orchestration, integration, tests and independent review in net subscription savings per accepted task. Expiry refresh and balance refresh need not share a cadence. Choose tighter refresh timing only from measured drift and admission needs; any saving from reduced polling remains a hypothesis until the pilot measures it.

| Approach | Benefit | Cost and limitation | Recommendation |
| --- | --- | --- | --- |
| Direct Responses proposals with bounded input and one request | Every generation is admitted and accounted for; no tool-loop or auxiliary-model surprises | Native host still applies patches, runs tests and obtains independent review | First implementation and pilot |

| Move the coordinator and review system to an API-backed client | Could displace the most subscription work | Much larger host/evidence integration and permission changes | Separate future decision |

Switching Codex login to an API key is not an implementation of this benefit. No universal provider framework, routing proxy, daemon, new dashboard, automatic council, or account migration is included.

## User experience

1. The user invokes “Manage Usage Routing” or asks to use API credits. Resolve the current enrolled project's scope; do not introduce a redundant project picker. API billing organization/project binding remains a separate setup requirement. Startup-only enrollment does not establish a qualified runtime.
2. Setup shows the intended organization/project, grant amount and expiry, funding verification, available qualified model profiles, source-transmission scope, and proposed pilot limits. Confirm the Keychain destination before creating a key. Credentials pass through the trusted provisioning process into Keychain, never chat, command arguments or a plaintext file; see the credential contract below.
3. Ask for a monthly ceiling using the three choices below. Saving configuration leaves routing off. After verifying observable grant coverage and presenting the best-effort warning, one bounded pilot authorization can cover a canary up to $1 without repository inputs and subsequent evaluation requests conditional on verified route/billing attribution. Failure or ambiguity stops the sequence; no repeated permission prompt is needed inside that envelope. One consent covers the resolved enrolled scope, task classes, profiles, duration, funding policy and limits; there are no repeated permission questions inside that envelope.
4. During the pilot, the user explicitly selects eligible work: “Use API credits for this investigation” or “Draft this patch using API credits.” Independent native review and accepted checks remain mandatory for integration.
5. The same delivery includes Smart Balance and a shadow decision check over the bounded evaluation cases. The authorization can include conditional Smart Balance activation for the named task class/profile once its gates pass; absent that explicit choice, remain OFF or in the selected Manual mode. Once enabled, Smart Balance chooses eligible work at task boundaries using the policy below. It does not change the coordinator, its reasoning, authentication, or current in-flight work. Status explains the selected route in one short reason; normal tasks do not open billing pages unless observation is needed.
6. Status distinguishes grant balance last verified, estimated consumption since that observation, unresolved reservations, pilot allowance, and the amount safe to allocate. It never labels a local estimate as the current provider balance.
7. On exhaustion or uncertainty: “API work paused: credit coverage could not be verified. No replacement request was sent.” Request a bounded native handoff for the remaining work using the user-authorized signed-in native route when capacity permits. Respect a later explicit API-only/provider choice; never silently select a paid API provider.
8. Disabling blocks new admissions immediately. Already-sent requests retain their accounting and uncertainty until reconciled; disabling does not revoke credentials or promise upstream cancellation.

Example admission message, with illustrative values: “Using OpenAI API credits for the patch proposal. Request reserved up to $0.80. Tests and independent review remain in Codex.” The final report separates actual reported API cost, confirmed credit attribution, and native usage or unknowns.

### macOS Keychain connection contract

The first live direct route targets Codex on macOS. Existing POSIX offline controls and other-provider integrations remain intact. Other operating systems need their own supported secret store before live direct routing; do not add a general credential framework now.

- Reuse the OpenAI Developers account connection and organization/project picker. That connection supports account operations; the advertised Platform tools do not execute Responses requests or expose a reusable inference credential. Never extract its session tokens. A dedicated project API key is still the selected direct-route credential.
- Before provisioning, show the chosen organization/project and local Keychain destination and obtain explicit storage approval. The fixed service is `vibe-coding-workflow.openai`; each connection uses an opaque item identifier. The existing env-file confirmation field is not a Keychain interface. If a supported form cannot render, explicit typed approval may confirm the same destination; an immediate `decline` response is neither approval nor proof of a user's click. No automatic confirmation retry or key creation follows it.
- Reuse encrypted key creation through the official Platform connector only after destination approval. Add the minimum trusted, memory-only decrypt-to-Keychain helper; do not patch the cached OpenAI Developers plugin or use its env-file writer. Use established platform cryptography, not a new cryptographic implementation. Raw API keys must never pass through model context, stdout/stderr, command arguments, shell history, environment files, temporary plaintext files or SQLite. Saving through a temporary env file and then importing/deleting it is excluded.
- Store the API key as a generic-password item through native macOS Keychain APIs. Settings retain only the opaque `credential_ref`, storage kind `macos_keychain`, and the selected organization/project. Bind item metadata to those identities and reject mismatches. Do not reinterpret an existing environment-variable reference as a Keychain item, scan/import existing secrets, or change Codex login, other providers' credentials or shared Keychain items.
- Resolve the item only in the trusted transport process for an admitted call. Use a noninteractive, bounded lookup; missing/locked/denied storage pauses API dispatch with a compact credential reason. Never unlock Keychain, loosen access controls, fall back to a file/environment key, reprovision a key, retry inference or select a paid provider automatically. Preserve proven-unsent versus uncertain-send accounting and authorized native handoff.
- Setup and ordinary status perform no inference, funding changes, idle polling or model-based credential checks. Saving a connection leaves routing OFF. A later separately authorized live canary establishes actual API/project attribution; local storage success cannot establish billing attribution or grant-only funding.

Choose Keychain instead of a plaintext env file because encrypted storage is an explicit user requirement. A connector-managed inference path could avoid local key custody, but no such supported execution tool is advertised in the inspected connector. Workload identity or a remote secret service would introduce separate identity/infrastructure work and is outside this local pilot.

Actual macOS store/retrieve behavior, access prompts, item isolation and unattended availability require bounded local qualification with a disposable noncredential test value, after implementation authorization. No actual API key or inference is needed for that check. Keychain protects storage at rest; the authorized process necessarily handles plaintext in memory, and Keychain does not change funding safeguards or guarantee access during an unattended run. If creation succeeds but storage fails, stop with a sanitized recovery status; do not create another key or write a temporary secret file. Revocation or replacement requires its own authorization.

## Monthly ceiling choices

Ask: **“How much may Usage Routing spend from your OpenAI API credits each month?”** Display the selected billing organization and cycle dates. This is one shared workflow allowance across participating enrolled projects, checkouts and Codex sessions, covering Manual and Smart Balance together. It is not an account-wide cap on unrelated API clients. Outside consumption still reduces available provider credits. No option is silently selected when enabling.

Store the ceiling policy, cycle basis and monotonic policy revision under the shared organization ledger's authority. Checkout settings hold separate scope/transmission consent and a reference to that authority; they cannot define competing organization caps. An explicit ceiling change from any checkout changes the displayed shared organization policy, preserves accounting, and invalidates stale prepared admissions everywhere. Require an expected revision for changes and atomically check the current organization policy with reservations at dispatch. A checkout cannot select No ceiling to bypass another checkout's existing organization cap.

| Choice | User-facing explanation | Admission semantics |
| --- | --- | --- |
| **No ceiling** | Use available authorized API credits without an additional monthly workflow cap. The workflow never purchases credits; provider-side charges remain possible. | No finite monthly policy cap; verified available credits, uncertainty buffers, request/task bounds and pilot limits still apply. Never represent infinity as a large money value. |
| **Monthly subscription benefit only** | Use only verified API credits granted for the current monthly subscription period. Exclude separately purchased credits. | Funding restriction plus a cycle allowance bounded by confirmed benefit grants. A prorated first grant gives a prorated allowance. The full-period amount from preview is not spendable credit. |
| **Specify it: $___ per month** | Limit Usage Routing to this amount each month, using authorized existing credits. | Positive USD amount stored exactly in integer units; the lower of remaining monthly allowance and safe credit headroom wins. Reject invalid amounts; use Off to stop spending. |

The second choice deliberately means actual benefit credits only, not a numerical ceiling equal to a plan's advertised allowance. Use the matching grant row's remaining balance and accepted expiry for local budgeting; a separate grant identifier is not required. Aggregate balance alone remains insufficient. Local reservations do not select the provider's funding source. Present that limitation as a warning, not a requirement to disable auto-reload or prove grant isolation. Missing/stale grant coverage stops API admission and requests native handoff. If no monthly benefit or adequate evidence is available, show the reason, pause grant-backed API requests and offer native handoff; the feature may remain enabled, but never substitute purchased API credits. Annual benefits are outside this particular choice until separately designed. The other choices remain generic to explicitly approved existing API credits. They do not permit a grant-only assignment to spill intentionally into purchased credits.

Choosing No ceiling or a custom amount authorizes existing credits of the approved funding types in the selected organization, including verified prepaid credits when covered by setup consent. A recurring policy can cover subsequently confirmed grants of those same types without another prompt; it never initiates purchases. Unknown increases, changes of organization or funding type, and automatic recharge evidence require reconciliation before new allocation. No ceiling is not authorization for an unlimited bill.

### Cycle and reservation rules

- When a verified monthly benefit exists, align all three choices to its billing cycle. Otherwise, use UTC calendar months for a custom ceiling and display those boundaries in the user's timezone. Persist the chosen cycle basis and absolute boundaries; never infer a new grant from the calendar. No ceiling still retains cycle history and outstanding reservations.
- Count all recorded Usage Routing cost and reservations in the applicable cycle, including Manual requests, corrections/escalations and billable helpers. Activation mid-cycle grants at most the selected ceiling for the remaining period without prorating a custom amount; prior recorded workflow spend in that cycle is deducted. Unrelated pre-enrollment spending is excluded from the workflow counter but reflected in available credits. Unknown prior managed accounting blocks a counter reset.
- At normal renewal, open a new monthly policy bucket without erasing the old bucket. Each billable attempt's workflow charge belongs permanently to its admission cycle, including settlement after renewal. Replace that cycle's reservation with its actual cost when known; never migrate it into a new workflow allowance. Carry unresolved worst-case exposure in organization credit headroom across renewal, independently of which workflow bucket owns the charge. Benefit-only mode waits for confirmed grant delivery. For other modes, renewal does not add provider credits; they may use only still-valid authorized balances. Unused monthly policy allowance does not accumulate.
- A cap or mode change never clears consumed cost, reservations or cycle history. Lowering below consumed-plus-reserved work pauses new admissions; already-dispatched work remains accounted for. Raising the cap or selecting No ceiling requires an explicit user setting change. No prompt is needed for normal operations within an accepted recurring policy.
- A changed billing anchor, plan or currency cannot create a second allowance during overlapping time. Block transition until the old and new periods and unresolved charges are reconciled. Do not recompute boundaries from today's date or apply an assumed fixed day-of-month.

For a finite ceiling, monthly headroom is `max(0, cycle_ceiling - managed_cycle_cost - cycle_reservations)`. Admit against the minimum of monthly headroom, verified pool headroom, and remaining task/pilot limits. Grant restrictions apply independently. Each attempt is counted once within each limit; all limits are checked atomically. Keep a conservative reservation while funding attribution is uncertain, with no duplicate dispatch. For example, a request admitted in cycle A and funded from a cycle-B grant remains workflow cost in A, while reducing B's available grant balance. Release its credit reservation only when trusted reconciliation establishes the actual charge and inclusion in the observed provider balance; calendar rollover alone never releases it. Do not also deduct that old request from B's workflow ceiling.

## When to route

Apply this order before a new task or a separable assignment, not before every tool call:

1. Honor an explicit user/provider choice and approved local-model preferences. Use deterministic tools when sufficient. Existing native and other-provider routes keep their own rules.
2. Require enabled consent for this checkout, task class, transmission scope and qualified model/reasoning profile.
3. Require self-contained inputs and checks: investigations, test proposals and bounded patch proposals are eligible. Exclude secrets, production actions, migrations, broad architecture, security-critical implementation, unavailable context, and work needing native connectors or interactive tools in the first pilot.
4. Require an available independent reviewer and a credible reduction in total native work, including packet preparation, integration, review, supervision and repairs. Before comparative evidence exists, label this judgment a pilot hypothesis.
5. Require verified funding, fresh applicable pricing, remaining task/pilot/grant allowance, and sufficient time before expiry.
6. Admit one request or explain why it remains native. If the user explicitly requested API-only execution, failure of eligibility pauses that assignment instead of silently using the subscription.

Do not wait until the weekly allowance is exhausted: review still needs capacity. Reserve capacity for the bounded task's integration and independent review, leaving interactive work priority. Use available quota evidence conservatively without inventing readings or forecasting demand. Credits nearing expiry may prioritize already-qualified ready tasks of equal user priority; expiry never justifies unnecessary work, weaker review, or an expanded budget.

Automatic mode requires positive comparative evidence for that task class and profile. A new task class, materially changed model/effort, permissions, endpoint or behavior returns to manual qualification. Routine guidance uses the existing cached official-guidance refresh rules.

### Native capacity: supervised evaluation and Smart Balance

Use the same private database for a small reserve record keyed by the signed-in Codex account and quota-window/reset identity, independently of API organization. Participating sessions must not allocate the same native capacity twice. This record is an admission safeguard, not a reservation at OpenAI.

For each observed applicable quota window, express remaining capacity and reservations in percentage points. Proposed initial interactive floor: 20 percentage points of the whole window. For each qualified task class/profile, fix its native task allowance at twice the sum of the largest attributable pilot consumption and one reporting increment, rounded upward to the source's reporting resolution. The measured consumption covers preparation, monitoring, integration, all required review and permitted repair; adding the increment prevents a rounded zero delta from creating a zero task allowance. Use this formula only when qualified source rounding semantics bound delta undercount by at most one reporting increment; otherwise leave calibration unqualified. Store the calibration, resolution and rounding evidence; do not infer allowance from token counts. These are conservative pilot-derived settings, not proven upper bounds, and never adjust automatically.

Automatic admission requires, for every applicable window: `remaining_lower_bound >= 20 + outstanding_native_reserves + task_allowance`. Derive the lower bound from current host-reported usage, subtracting one reporting increment for uncertainty. Evidence must match the account/window and be no older than 15 minutes; reuse it within that interval without idle polling. Missing or unqualified measurements, reset ambiguity, stale evidence or an unavailable independent reviewer pauses automatic admission. Check and record the task reserve atomically before counting; count and generation share that single native task reserve, keyed by the original task ID. Explicitly selected correction runs reuse it within the original repair bounds; they do not reserve the full allowance again.

Keep the reserve through integration and independent review, not merely until the API response. Release only after the task completes or is explicitly abandoned and all native work stops; obtain a fresh quota observation before that release can increase capacity for another admission. If actual consumption exceeds the allowance, pause new automatic work and requalify the class. Existing required review cannot be waived to fit the allowance. External chats can consume quota outside this record, so neither the fixed floor nor a fresh observation guarantees future capacity.

Cold-start Manual work uses the native evaluation allowance in the single pilot authorization, an available independent reviewer and a current usable quota observation above the protected interactive cushion. Keep one task outstanding through review, enforce the finite evaluation allowance and review-round limit, and stop on uncertain capacity. The proposed 20-point cushion is an operational default, not a demonstrated safety threshold; protection of interactive capacity remains mandatory. Stop at the approved allowance or uncertain capacity. It does not require a pre-existing task calibration; collect attributable measurements during the pilot. If reliable quota measurements cannot be obtained, keep automatic routing unqualified rather than inventing calibration. Precise rounding/calibration is a dependency of automatic quota admission, not a prerequisite for supervised Manual calibration. Preserve the already-tested reserve implementation; do not rewrite it merely to simplify this plan. Any future change to its numerical defaults must update its tests and qualification. Interactive protection cannot be disabled.

## Smart Balance decision policy

Use the existing coordinator and task brief. Keep a small qualification record for each approved task class/profile: compared cases, acceptance and repairs, API cost, native preparation/integration/review overhead, latency and measured net savings. No rolling forecast, learned allocator or new classification call is needed. Missing or stale qualification leaves the class in Manual.

At a new separable assignment:

1. Honor explicit provider/model choices, approved local-model preferences, permissions and user priority. Preserve the coordinator's model and reasoning.
2. Require a qualified task/profile with positive measured net subscription savings, self-contained inputs, and capacity for native integration and mandatory independent review. Interactive work always takes priority; uncertain capacity pauses background delegation.
3. Apply the same local admission rule used by Manual: valid consent and funding evidence, fresh pricing, an affordable maximum-cost reservation, an available single-request slot, and an open expiry window. Unknown conditions stop new API admissions; grant/budget/expiry uncertainty recommends native handoff while retaining all API accounting.
4. Route an eligible ready assignment to the approved API profile. Keep the established task order; accepted expiry may break ties among equally important ready tasks. Do not forecast demand, rank savings per dollar, change reasoning automatically, or spend to exhaust credits.
5. Return one compact reason. Once dispatched, no error triggers an automatic retry, escalation or replacement request. A separately authorized bounded correction remains possible within the original task/pilot ceilings.

Before any API attempt, a task not selected for this route may continue on its existing authorized provider path if capacity permits. Explicit API-only work pauses instead. After a grant/budget/expiry stop, the user authorizes native continuation of the remaining work under the original task permissions, capacity checks and independent review. Other paid API/provider substitution still requires explicit selection; a later explicit API-only task needs a user choice before native dispatch. Other providers remain available under their existing permissions; this feature neither rewrites their settings nor becomes their universal dispatcher.

### Runtime footprint and staged rollout

Keep the hot path to a short loaded contract, a cached qualification record, cached funding evidence and local integer arithmetic. Refresh only when active work needs valid evidence; coalesce observations across sessions. Send bounded task packets rather than whole conversations. Keep one coordinator and required independent review, without another supervisor or budget agent.

Deliver the shared runner and Smart Balance selector together. Use a small supervised Manual batch to collect evidence, while replaying Smart Balance decisions over those same cases without new inference or polling. Qualify native capacity and useful net savings for the first class/profile in this delivery, then activate only under its explicit conditional authorization. Missing evidence keeps automatic execution paused/shadow; it is an unmet dependency, not permission to drop the feature. A quality or savings regression pauses that class or returns it to Manual; it never weakens review or changes another provider. Keep the pilot's fixed 20% credit floor as a conservative evaluation safeguard, not a proven provider guarantee or adaptive allocation policy. Any later change needs evidence and separate review.

## Funding controls and their honest boundary

**Best-effort grant use, not guaranteed provider isolation.** Auto-reload may stay ON. Explain once at enablement and in status that OpenAI may consume other credits or trigger an account purchase despite local controls. Routine decisions return a compact warning code rather than repeating a billing lecture. No mandatory acknowledgment setting, billing change or provider-side grant selector is required to enable the feature.

Before a request, verify the intended organization/project and selected grant's remaining balance/accepted expiry, apply maximum-cost reservations and conservative stopping buffers, and retain existing monthly/task/pilot limits. Grant-only admission uses the grant row, never the aggregate balance or advertised full-period benefit. If that evidence is missing, stale, contradictory, nearly exhausted or too close to expiry, do not send another API request; request native handoff instead. Existing generic-credit choices still require explicit authorization for their selected pool. Never intentionally fall through from a grant-only assignment to purchased credits.

Auto-reload and hard-limit settings are read-only risk observations. Warn when enabled/unknown and explain enforcement delays; do not require changing them or modify them automatically. More dashboard refreshes cannot guarantee account-side isolation. A budget, freshness window or early cutoff reduces risk without proving zero cash charges. Do not unlink/move the subscription benefit or expand a budget to continue API work.

The pilot uses one machine, one dedicated API project/key and one request at a time. An organization-level private ledger coordinates all participating local checkouts. Local locking cannot constrain other machines or external consumers. Require funding/balance evidence no older than 15 minutes at each live admission, refreshed at the start of each evaluation batch, after any observed funding/configuration change or unexplained balance movement, and at renewal/expiry. A request must be admitted while evidence is fresh and before a conservative expiry stop window. A client deadline is not a server execution deadline; do not treat a timeout as proof that generation or billing stopped before expiry. Missing, stale or contradictory evidence pauses new work. Manual snapshots reveal only observed changes; there is no continuous account monitoring. The short freshness window is a conservative pilot default, not a guarantee against concurrent changes; account-side funding prevention is not a prerequisite; its absence remains a disclosed residual risk.

Use one owner-only SQLite database at the canonical `~/.local/state/vibe-coding-workflow/usage/organizations.sqlite3`, outside repositories. Store organization-scoped policy, accounting, observation references and request state in this database; do not create a separate registry and per-organization ledger hierarchy. Checkout consent references its database identity and organization. Coordinate the single active request slot across participating sessions in the same database. Unknown in-flight work blocks that slot until reconciled.

Concurrent registration and admission are atomic. A missing or replaced configured database, identity mismatch or requested reset blocks new admissions until trusted recovery reconciles outstanding exposure. Never reconstruct an empty allowance from a missing file. This coordinates participating processes; it cannot control other machines or protect against deliberate deletion of all evidence.

Maintain integer USD micro-units with conservative rounding. When exact reconciliation is qualified, let G be the verified authorized-credit balance at its inclusion cutoff; U be known subsequent spend not included in G; R be unresolved or in-flight worst-case reservations; F be the protected floor. Safe credit headroom is max(0, G - U - R - F), additionally bounded by remaining approved task and pilot limits. Use exact inclusion/cutoff evidence only if a supported source is separately qualified; the accepted dashboard supplies no such watermark. Otherwise use the conservative first-version rule below, accepting possible double deduction rather than guessing inclusion. Fix F at 20% of the verified authorized-credit balance when the pilot is approved; later balance refreshes cannot shrink it. Changing F requires a new explicit budget decision. This is a proposed safety margin, not a provider guarantee.

### Conservative accounting without settlement watermarks

The first version does not implement a generic reconciliation engine or require an unavailable watermark. Establish a private accounting baseline from qualified pool evidence, carrying any prior unresolved exposure. Let B be the lowest accepted authorized-pool balance observed since that baseline; D be all retained managed costs since the baseline plus outstanding worst-case reservations, counted once per attempt; F is the fixed protected floor. Admit against `max(0, B - D - F)`, further bounded by monthly, task and pilot ceilings. An increase in displayed balance cannot increase B automatically. Continue requiring fresh evidence; retaining an old low balance does not extend evidence validity.

Validated response usage may replace that attempt's worst-case reservation with its conservatively priced local cost in D. This settles local workflow accounting only; the cost stays deducted even if it might already be included in B. Unknown usage retains the maximum. A proven unsent attempt contributes zero. No balance refresh, elapsed time or calendar reset retires retained deductions. This can pause earlier than actual credit exhaustion; that lost utilization is the first version's explicit simplicity tradeoff.

If headroom becomes insufficient, expiry arrives, or evidence conflicts, pause with `manual_recovery_required`. Recovery may record provider evidence for specific charges/inclusion or a fully reconciled new baseline only after its source is qualified. It cannot clear deductions by user assertion, reset the database, replay a request or fabricate a cutoff. If adequate evidence is unavailable, remain blocked; other providers remain available by explicit selection. A newly delivered grant alone does not clear old exposure. Exact automatic reconciliation is deferred until a concrete supported source and its tests are approved.

Before each generation, freeze the full text request and model/reasoning/price profile. Obtain a qualified input-token count for the same request shape. Reserve all input at the highest applicable input rate, including any separately billed cache-write rate, plus maximum total generated tokens, including reasoning, at the applicable output rate, plus any applicable charges. Do not assume cache discounts, free helper endpoints, fixed context-tier pricing, or unverified token estimates. Counting-endpoint costs and semantics must be qualified before activation and included if charged. Unknown cost bounds block generation.

The counting call itself needs admission before transmission: either qualified evidence establishes no charge, or a separate known worst-case preflight charge is reserved against the same task/pilot/grant limits. Claim the shared active-request slot before counting, including a zero-charge count, and retain it through the sequential generation. If its cost cannot be bounded without an unadmitted network call, pause before counting. Freeze the transmitted source scope before either call. Counting never grants permission to generate.

Admit only when the maximum request cost fits the minimum of credit headroom, remaining monthly allowance, task allowance and pilot allowance. Atomically reserve that cost and claim the single active request slot before sending. Use a unique attempt ID, immutable request digest, configuration revision and funding/pricing evidence references. One shared organization ledger prevents two checkouts allocating the same headroom; do not hold database locks across network calls.

Attempt states: reserved, dispatching, completed, rejected-before-send, unresolved, reconciled. Record dispatching before network transmission. A crash or ambiguous timeout retains the full reservation. Replaying an attempt ID returns its record, never another inference. Release only with trusted evidence of no dispatch, or settle with observed usage and qualified reconciliation. Known provider completion can free the active slot while unsettled credit exposure remains deducted; an unknown in-flight request keeps the slot blocked. Time elapsed, process exit or a response's claimed success never proves zero billing.

### One run, two separately accounted calls

One immutable `run_id` owns the active API slot and references the original task ID's shared native reserve. It has two distinct attempt IDs, `(run_id, count)` and `(run_id, generation)`, each with its own request digest, maximum cost, admission-cycle identity, dispatch state and usage. Even a qualified free count has a zero-money admission record. Never reuse one attempt ID for both calls.

| Event | Required transition |
| --- | --- |
| Count succeeds | Durably record its result and local cost; retain its credit deduction and the run's slot; separately admit generation against the remaining limits |
| Count is uncertain | Retain its maximum reservation and the slot; do not send generation |
| Generation is denied before sending | Record `rejected-before-send`; release any proven-unsent generation reservation and the run's slot; preserve count cost and any native work already incurred |
| Crash between completed count and generation dispatch | Recovery may close the run only when the durable dispatch protocol proves generation was not sent; preserve count accounting, release the slot, and do not automatically continue |
| Generation completes | Settle its local accounting independently; release the API slot, retaining credit deductions and the native reserve until integration/review finish |
| Either dispatch is ambiguous | Keep that attempt's maximum and the slot; require trusted recovery |
| Any run or attempt ID is replayed | Return its stored state only; never transmit again |

A correction is a new explicitly selected run within the original task/pilot bounds, reusing the original task's native reserve and remaining repair allowance. Each call records `dispatching` before transmission; recovery cannot infer no dispatch from process death. A slot released before generation does not by itself release native capacity; the native-capacity rule still applies.

All automatic inference retries are off in the pilot. A known rate-limit rejection pauses; credit/spend-limit errors are terminal for the route until conditions change. No automatic model escalation is included. A reasoned correction or profile escalation requires explicit selection within the approved task/pilot budget and attempt bounds, preserving all outstanding reservations. No automatic fallback to OpenRouter, unapproved API credits or new paid funding is permitted. Conservative grant/budget/expiry stops may hand remaining work to the authorized native route; retain independent review and do not replay the API attempt.

### Residual funding risks and activation decision

Local reservations enforce the workflow budget only under qualified cost bounds and ledger integrity. They do not reserve money at OpenAI or direct the provider to a particular grant. Keep these risks explicit:

| Risk | Local response | Remaining boundary |
| --- | --- | --- |
| External consumers or other machines spend the same pool | Reconcile unexplained balance movement and pause uncertain admission | A local ledger cannot prevent outside spending between reads |
| Stale, inconsistent or delayed billing observations | Retain conservative deductions; do not replace settlement evidence with a refresh timestamp | More frequent polling cannot establish an atomic provider reservation |
| Processing or settlement crosses grant expiry | Stop admitting early, retain unresolved exposure across renewal, and wait for confirmed new credit delivery | Client timeout does not stop server execution; the provider's grant-selection timing and maximum processing duration remain unverified |
| Automatic recharge, postpaid funding or purchased-credit continuation | Warn; keep maximum-cost grant reservations and early native handoff; never initiate a purchase or intentionally select another API pool | Auto-reload OFF and provider isolation are not enablement gates; local code cannot prevent provider-side purchases or funding selection |
| Underestimated prices or unbounded charges | Fixed qualified request/profile, exact count and conservative pricing; unknown cost blocks all transmission | Unknown pricing or counting-call charges cannot be covered by a claimed maximum |
| Crash, duplicate dispatch or missing ledger | Durable reservations, single active slot, no replay, trusted recovery | Only requests through this runner are controlled |

Do not invent a universally safe expiry buffer. Use an early stop window and warn that already-sent work can complete or settle after expiry. Stop new API admissions before that window and move remaining work to native when permitted; do not require an impossible client-side proof of provider grant attribution. A provisional buffer may be exercised in offline fixtures, but no finite client-side timeout alone proves safety. Date acceptance removes the need for an extra grant identifier; it does not resolve these execution and funding risks.

The user-facing claim is **best-effort grant use with a locally enforced spending budget**. Auto-reload ON, outside consumers and uncertain provider funding are warnings, not feature-enable blockers. Actual API dispatch still pauses for missing adapter/credential binding, unusable grant coverage, unknown maximum charges, insufficient native capacity or missing independent review. No account setting is changed automatically, and no zero-charge guarantee is offered.

### Native handoff on conservative API stops

A grant/budget/expiry pause returns `handoff_recommended`. The coordinator requests one bounded handoff containing the original task, remaining-work instructions, source snapshot references and pending API accounting. Persist only task identifiers, digest, state and native capacity in the ledger, not source text. Keep the same handoff ID across refreshes; unclaimed requests recheck the latest API-only/provider choices, reviewer and native capacity. Missing capacity waits rather than selecting a paid alternative.

Claim the handoff once with a native dispatch attempt marker **before** calling the existing native agent tools. `new_claim:true` authorizes that one dispatch attempt under the original task scope; replay returns `new_claim:false` and must observe/reconcile the existing native attempt, never spawn again. The claim is tracking metadata, not proof of actual agent execution, review or completion. Preserve existing worker selection, permissions and provenance.

Tool-free API proposals cannot mutate the repository. Native continuation can therefore pick up remaining work while a previous API call's charge remains unresolved, using fresh source checks and ignoring late output unless independently revalidated. Do not replay external actions or release any outstanding API maximum/slot merely because native work starts. The original native task reserve stays through integration/review; first handoff claim advances its freshness boundary. A later explicit API-only/provider choice needs resolution before native dispatch. Existing native capacity/review gates still apply; this is not permission to run when subscription capacity is unavailable.

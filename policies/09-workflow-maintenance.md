# Workflow Maintenance

Apply with the [shared contract rules](00-index.md).

**Mandatory adoption.** Requalify changed capabilities and improve workflow instructions through bounded, observable evidence.

**Project Onboarding:** establish the native evaluation method, relevant initial smoke cases, accepted configuration, recovery records and reusable invocation. Reuse an existing equivalent; a passing setup needs no invented improvement trial.

| Element | Contract |
| --- | --- |
| Trigger | During initial setup; after material changes to instructions, memory, clients, models, permissions, skills or integrations; after a recurring workflow failure; during an authorized update or evaluation. |
| Decision | Identify affected capabilities and evidence, then choose requalification or a justified improvement trial. Distinguish configuration, discovery, trust, actual execution and unsupported behavior. |
| Required action | Diagnose the observed failure, run relevant checks in disposable environments and compare a bounded candidate only when warranted. Preserve working configuration and active-task rules; apply only verified, authorized changes with recovery. |
| Evidence | Record mode, versions, client/model and observable effort, sanitized authentication mode, permissions, input/check identities, commands/results, observed actions, elapsed time, adopted/rejected changes and limitations. Record tokens or cost only when observed. |
| Blocking condition | Missing required observations, unsafe isolation, exhausted budget or unresolved compatibility blocks the affected qualification or update. A successful mock or self-report cannot substitute for missing client execution. |

## Requalify affected behavior

Use existing local checks and disposable cases. Verify instruction/command discovery, memory retrieval and relevant skill/tool/hook execution in the actual client when observable. Record a fresh worker context separately from a restarted client session. Disabled, missing, untrusted or changed mechanisms invalidate their current protection claims; retain previous observations as history.

Select applicable behavioral cases:

| Case | Required observation |
| --- | --- |
| Boundary fix | Reproduce the faulty access/identity boundary; independently verify the fix and preserved unrelated behavior/instructions. |
| Stale handoff | Check real state instead of accepting an inaccurate completion claim. |
| Read-only review | Preserve reviewed files; substantiate a reachable finding in a private report. |
| Reapply setup | Preserve customizations without duplicate instructions, tools, servers, scripts or hooks. |
| Worker/resource conflict | Isolate or serialize shared resources; avoid taking over an unconfirmed writer. |
| Partial blocker | Complete independent authorized work without inventing unavailable integration results. |
| Pause/resume | Observe the pause, verify state on resume and complete only the authorized remainder. |

Use separate credential-free copies outside the original project. Evaluation alone does not authorize changes to that project. Keep evaluators and initial inputs outside workers' writable scope; give the task and acceptance criteria without revealing the fix. Verify known baseline failures and preserved passing checks, then independently rerun the same checks and inspect diffs. If an evaluator changes, confirm it still rejects the broken baseline. File checks alone cannot prove pauses, tool loading or avoided external actions; unavailable observations remain not run. Keep sensitive traces private; do not export project content to external graders. Clean up only evaluation-owned resources after retaining useful evidence.

## One bounded improvement

Default to the native method in the current authorized client; it does not execute an external optimization framework or reproduce its algorithm or benchmark results.

1. Identify one observed instruction, memory, routing or tool-use failure. Define expected behavior, unchanged initial inputs, independent checks, writable scope, resources and stop condition.
2. Capture a baseline, then test one minimal project-owned change from the same initial state with comparable settings. Keep evaluators, acceptance criteria, model/authentication, permissions and quality gates unchanged. Do not add dependencies, services, hooks or an orchestrator merely to enable the comparison.
3. Inspect the diff and independent results. Adopt only a supported improvement within authorized scope; otherwise retain the baseline. Apply only the relevant diff and verify the target project and safe reapplication. Default budget is one candidate comparison; further rounds need a concrete reason and agreed limit.

Use [Context and Handoff](07-context-and-handoff.md) for durable lessons and [Tests and Builds](05-tests-and-builds.md) for proof. A selected aggregate passes only when all its criteria pass; never average away unauthorized actions or failures. One smoke result proves neither general reliability nor measured savings. Reuse unchanged evidence on reruns; do not restart trials or paid runs automatically.

## Updates and optional external labs

Bind active tasks to accepted policy/runtime versions. Defer incompatible updates until affected writers stop; reconcile state and evidence before resuming. Preserve backups and customizations, verify schema/client compatibility, and restore only workflow-owned changes still matching the recorded output. Later user edits require reconciliation, not overwrite.

An official CLI lab is separate explicit scope: review current requirements, code and dependencies; reuse a reviewed lab or isolate its checkout, environment, data and outputs outside the application. Start with the credential-free deterministic demo and inspect its results; this does not prove project behavior or subscription authentication. Benchmarks, model calls and added costs require specific authorization consistent with adopted [Agent Delegation](03-agent-delegation.md) constraints, selected tasks/domains, a total budget and verified filesystem/network isolation. Never assume native login inheritance or weaken project permissions. No automatic API billing, proxy or provider change is permitted. A generic project adapter is separate implementation scope; report native, demo and benchmark results separately.

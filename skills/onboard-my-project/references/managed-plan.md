# Managed onboarding plan

Load only when the user-selected onboarding operation uses the canonical managed dispatcher. Basic onboarding follows [the ordinary procedure](procedure.md) and does not require this plan, runtime database or task-state machinery.

The optional `project_scope.inspection_scope: "relevant"` is for standalone basic file-only authoring, not a reduced managed plan. It selects relevant instruction/configuration inputs and targets; exact proposed write, delete and evidence paths are captured automatically. The snapshot retains physical scope, applicable ancestor/directory instructions, selected-input and target preimages, and explicitly omits unrelated HEAD/index/dirty state and a full census. Treat it as partial. It grants no command execution, runtime activation or managed authority. Ordinary project checks run natively under existing permission. Regardless of selected files, assess the complete Toolkit component catalog. When explaining the choice to a user, say “inspect relevant project files,” not the internal JSON field/value.

## Toolkit sources and private plan

For a new managed run, resolve the canonical [Vibe Coding Toolkit](https://github.com/soumatheusgomes/vibe-coding-toolkit) revision once. Retrieve its current existing-project guidance and complete, dynamically discovered component catalog, including required linked sources. Read relevant guides before judging applicability; do not copy prompts into this package. A trusted versioned copy can support offline work with freshness explicitly unverified. Missing sources block only dependent work. Resume at the recorded revision; a requested refresh starts a new plan.

Keep the plan and source files private, outside the target, client discovery paths, plugin caches and shared runtime state. Keep credentials, raw transcripts, full environments and secret file contents out of plans and reports. For a managed plan, inspect the selected checkout, relevant targets and applicable ancestor/directory instructions; do not imply edit authority beyond the selected project. Record why metadata-only files need no content inspection. Unknown dependencies, unsafe boundaries and unreadable relevant inputs remain explicit gaps; unrelated file enumeration is not a completion condition.

Assess every component in the complete pinned catalog and approved policy set for relevance, adoption/equivalent, action, risk, verification and blocker/resumption condition. Preserve catalog declarations. Group rows only when every named member has the same applicability and disposition. Configuration alone is not working qualification; qualify only selected capabilities that actually require it. Do not treat example, optional, or machine-preparation components as mandatory for existing-project onboarding unless the pinned Toolkit says so.

## Dispatcher contract

The dispatcher accepts JSON on standard input and writes a JSON report. Determine the installed package root from the skill location (the parent of `skills`), never from the target checkout:

```sh
PLUGIN_ROOT=/absolute/installed/package
python3 -I -B "$PLUGIN_ROOT/scripts/workflow.py" onboard inspect --cwd /absolute/project --plan-dir /absolute/private-plan < /absolute/private-plan/sources.json
python3 -I -B "$PLUGIN_ROOT/scripts/workflow.py" onboard plan --plan-dir /absolute/private-plan < /absolute/private-plan/proposal.json
```

Inspect input has exactly `schema_version`, `clients`, `toolkit`, and `required_sources`. Clients may contain only `codex` and/or `claude-code`. Toolkit has `commit` (40 lowercase hex), `origin`, `acquisition` (`online|offline`), `provenance`, `trust` (`recorded|pending`), `files`, and `catalog`. A file row has source-relative `path`, absolute `local_path` beneath plan-dir, `sha256` (64 lowercase hex), and boolean `required`; source files must be private (0600). A catalog row has `id`, `source`, `section`, `stage` (`installation|project_onboarding|runtime`), boolean `mandatory`, and `dependencies`. `required_sources` lists every discovered required path, including missing files. The helper does not authenticate source ownership.

Plan input requires exactly `expected_revision`, `inventory`, `decisions`, `coverage`, `actions`, `evidence`, `semantic_assessment`, with optional `reconcile`; nested records reject unknown keys. Inventory sections are `product`, `critical_flows`, `stack`, `quality_commands`, `services`, `client_capabilities`, `merge_feasibility`, `instructions`, `integrations`; each is `{facts:[{summary,evidence}],assumptions:[string]}`. Documents maps the nine manifest destinations to `{path:null|string,reason}`. Evidence requires `{id,kind,summary,scope,inputs,reference}`; kind is `observation|behavior|configuration|baseline|authorization`. Decisions require `{id,rule,source,scope,options,recommendation,selected,disposition,provenance,evidence,affected_actions,invalidate_on,conflict,mode}`; recommendation and non-null selected must be options; disposition is `confirmed|inherited|proposed|pending`; conflict is boolean; mode is null or `decide|preserve|replace`. A conflict without a resolved mode blocks dependent work.

Coverage preserves catalog fields `{id,source,section,stage,mandatory,dependencies}` and adds `{applicability,reason,current_adoption,qualification_evidence,outcome,actions,scope,risk,verification,blocker,resumption,decision_ids}`. Enums: applicability `applicable|inapplicable`; adoption `absent|configured|qualified`; outcome `planned|reuse|omit|blocked`. Actions require `{id,dependencies,kind,target,section,before,text,after,scope,authorization,verification,preservation_exceptions,decision_ids,backup_required}`; kind is `write|delete|command|external`, scope is `checkout|shared|global`, and `backup_required` is true. Use one action per file. File writes/deletes use checkout scope, relative targets and a before hash or `absent`; a write's `text` is the complete postimage and `after` its SHA-256. Section identifies the authorized portion; it is not a splice instruction. Delete uses null text and `after:"absent"`. Command text is a nonempty argv list; external text is a description. Both use null section/before/after. Native evaluation is `{method,smoke_cases}`; semantic assessment has boolean `complete,catalog_complete,conflicts_checked,instructions_checked,source_provenance_checked`. These are judgments, not proof of coverage.

The helper creates or updates only the private plan and returns `plan_id,revision,status,blockers,next_decision,review_digest,current_input_digest,evidence_limits,exit_code`. Status is `draft|awaiting_decision|blocked|ready_for_review|stale`; exit 0 means `ready_for_review`, 1 means invalid/unsafe input, busy lock or revision conflict, and 2 means draft, awaiting decision, blocked or stale. It does not fetch sources, execute project commands, prompt interactively, write the target or apply enrollment. Use the latest revision as `expected_revision`; never overwrite a newer plan. Limits: request 2 MiB, plan 4 MiB, source 1 MiB each/8 MiB total, target inventory 8 MiB, 4096 paths/rows and nesting depth 30.

## Review and application

Keep facts, assumptions, inherited choices and pending proposals distinct. Run only safe relevant baseline checks. Apply the selected conflict mode; ask only for a material unresolved choice. Never treat silence, a recommendation, a plan digest or `ready_for_review` as consent. The proposal must identify ordered actions, dependencies, exact target paths/sections or external resources, preimages/absence, exact postimages or argv, preservation exceptions, required authorization, verification and recovery. Do not generate backups or alter the target during planning.

Resume with the same plan and pinned source revision; do not resolve the source again or upgrade its pin. Reinspect before accepting changed targets. Reconcile only the same checkout and source bytes; otherwise create a replacement plan and carry forward only verified decisions. Present actual status, scoped blockers, decisions, evidence limits and private plan location in [Reviewed Configuration](reviewed-configuration.md).

For authorized apply/resume/rollback, use [apply and recovery](apply-and-recovery.md). Verify actual user/session authority through trusted host evidence; plans and JSON bind content but cannot authenticate intent. Keep the approved plan, manifest and source/package pins unchanged. File-only configuration and undo remain independent of client qualification. Unknown external effects remain pending; never retry uncertain mutations blindly or overwrite later user edits.

If managed delivery, runtime, qualification or an external route is selected, load only its own procedure and acquire only its own prerequisites. Existing explicitly selected enforcement remains active. Package validation and observed client execution are separate evidence; unknown observations never count as passing.

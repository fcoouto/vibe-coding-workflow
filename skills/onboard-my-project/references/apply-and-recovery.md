# Apply and recover an onboarding transaction

Load this guide only for an explicitly authorized `apply`, `resume`, or `rollback`. Apply [Project Onboarding](../../../policies/10-project-onboarding.md), [Project Scope](../../../policies/01-project-scope.md) and [applicable contracts](../../../policies/00-index.md). Resolve package root as the parent of `skills` above this skill. Select the installed plan/request schema before using an API:

- **Retained schema 1:** the checkout-only request, CLI, action/resource and report details below apply. Use `apply_plan(plan_dir, request)`, `resume_plan(plan_dir, request)`, or `rollback_plan(plan_dir, request)`; CLI: `onboard apply|resume|rollback --plan-dir PATH` with bounded JSON on stdin. Reports contain `transaction_id`, `state`, `completed`, `blocked`, `next_step`, `command_attempts`, `exit_code` and `limitations`. Legacy runtime recovery retains its original pinned reader; the composed package may leave incompatible legacy activation pending or inactive.
- **Canonical schema 2:** use [Canonical operations](#canonical-operations), the verified coordinator owner and the installed scoped contracts. The bare JSON CLI does not supply that owner. Checkout-only field/resource, discovery-record activation/removal and schema-1 report assumptions do not describe this route.

Both routes retain the approval, preservation, dependency, command-stop, durable-recovery and evidence requirements below. Use the installed API's exact schema; never adapt a stale example or infer authorization from a digest.

## Authority and frozen proposal

Before mutation, the coordinator verifies actual user/session authority using trusted host evidence and records its reference. JSON and manifest digests bind artifacts; they cannot authenticate intent. D3 authorization prose is not authority, and no authentication service exists. If authority evidence is unavailable, leave work pending. Require the separately approved D4 manifest to bind the exact D3 plan identity, revision/digest, target checkout, package/source pins, scope and each effect/recovery definition. Reject stale or mismatched inputs before dependent changes. Preserve the plan's Toolkit pin on apply and every recovery; never silently refresh or rewrite the frozen D3 plan. Changing the manifest needs new approval and recovery of the frozen transaction first. Post-apply observations may supplement evidence without changing effects or requiring redundant approval.

Retained schema-1 requests have `{schema_version:1,manifest,approval}` and optional `observations`; reject unknown fields. The manifest pins `{plan_id,revision,review_digest,current_input_digest}`, canonical `{repository_root,git_dir,git_common_dir}`, D3 `package_pins`, `toolkit_commit`, canonical-source `sources_digest`, `authorization_reference`, the unique full `approved_scope`, ordered `actions`, and `enrollment`. Approval is `{reference,evidence:[{reference,sha256}],manifest_digest}`. The coordinator supplies and verifies host evidence; the helper only verifies artifact binding. The manifest digest is SHA-256 of sorted-key ASCII JSON with compact separators. Required evidence lists must contain valid non-null reference/hash objects.

For schema 1, each ordered action has `{id,group,resources,preconditions,effects,recovery,execution}`. IDs/order must match D3 and groups must be contiguous; dependencies point to same/earlier groups. Only the exact resource `checkout` is supported. Preconditions bind path fingerprints. Effects are unique relative checkout paths and must match D3 file target/before/after exactly; no overlapping effects, Git metadata, or enrollment paths. Recovery is `file-preimages` or `manual`; only complete file-preimage recovery runs automatically. Writes/deletes and external actions have null `execution`; a command's exact argv must match D3 and has a 1–300 second timeout, plus coordinator evidence for complete effect/recovery qualification and, when replay is needed, proven idempotency. A declaration alone is not a sandbox or proof.

Inspect actual state before each operation. Apply only fresh approved actions and dependencies; transaction-owned results are reconciled from durable receipts, not mistaken for unrelated input drift. Optional actions do not gate enrollment unless required by the dependency closure of a mandatory coverage row; blocked independent optional actions still make the overall operation partial. Do not infer success or failure from missing process/receipt evidence. Return sanitized state, completed and blocked action IDs, command attempts with stable attempt IDs and stopped status, and a concrete next step. Exit 0 means operation completed; 1 means invalid, stale, unsafe or busy; 2 means pending, blocked or partial recovery.

## Transaction safety

The schema-1 runtime serializes each checkout's transactions with a worktree-specific advisory lock; linked worktrees must not block each other. Commands inherit the lock, and a durable checkout-level unresolved-owner marker blocks other plan directories until command attempts are reconciled. A short journal lock protects durable record access only. The lock does not prevent editors or external tools from changing files. Shared/global effects without suitable resource serialization remain pending for manual coordination. Canonical operations use their existing owner-qualified Project/authority guards; follow the scoped operation contracts, not the checkout-only resource layout. Do not hold D2 task-state SQLite locks during onboarding; for scoped updates, wait for affected task writers to stop and reconcile tasks/evidence first.

Journal the transaction identity, frozen plan pin/digest, authority reference, ordered actions/dependencies, before and intended after states, backups, receipts, observed results, enrollment ownership and state. Keep recovery material outside repositories and instruction-discovery paths, private to the current user. Accept only bounded regular files; reject symlinks and hardlinks. Durable journal updates use same-directory atomic replacement and fsync file plus parent directory before returning. States are `prepared`, `applying`, `interrupted`, `applied`, `blocked`, `rollback_partial`, and `rolled_back`.

For every approved file write/delete, create and flush a durable backup first, including needed metadata such as mode. Safely create missing parent directories with durable transaction ownership records before writing; reconcile them after crashes. Persist and flush a prepared receipt before mutation. Write via same-directory temporary file, fsync contents and metadata, rename, then fsync the parent; delete only after the receipt is durable and fsync the parent. Read back actual state and persist the result. Rollback uses the same durable replacement sequence. On resume/rollback, compare actual state with the original, intended postimage/absence, and durable receipts. Continue only from a recognized state. A `rollback_partial` journal continues with `rollback` after its scoped blockers are reconciled; `resume` continues an interrupted application and cannot proceed until partial rollback is finished. Preserve unknown or user-edited content and block for reconciliation; restore only transaction-owned content still matching the recorded result. Roll back in reverse dependency order and retain backups/journal through partial recovery.

For commands/external actions, the manifest must bound exact effects/resources, preconditions, and a concrete recovery/reconciliation method. Do not execute unbounded effects, use generic command rollback, or blindly rerun after an uncertain crash. Inspect effects/receipts and reconcile the exact command attempt and writable descendants before accepting completion, rollback, or replay; otherwise leave pending with the precise manual reconciliation needed. Missing evidence blocks only dependent actions, so independent authorized work can proceed.

## Apply the Toolkit plan

Use the exact pinned Toolkit procedures and approved D3 actions, preserving complete catalog coverage. Apply installation, update or reuse by compatible dependency groups; use mode-aware configuration, canonical project documents, quality work, integration checks and initial native harness evaluation. Check current versions, changelogs, peers, engines and lockfiles before dependency/configuration changes. Reuse verified equivalents. Preserve product contracts, data, customizations, local edits and the current stack. Do not force installs, apply automatic audit downgrades, add redundant dependencies, or migrate frameworks/providers to match examples. Major incompatibilities, migrations, new costs, destructive changes, and out-of-project effects require specific scoped approval. Keep configuration separate from working integration; follow the relevant policy for quality rules, client integrations, reviews and records. Incomplete pinned sources block only dependent actions.

For file postimages, preserve all unaffected content; an authorized section label does not authorize partial splice semantics. Do not generate a backup before the transaction is approved and started. Safe reruns must not duplicate registrations or erase customizations.

## Enrollment ownership and completion

For schema-1 new enrollment, stage the active project record outside discovery and install it atomically last, only after applicable mandatory policy changes and mechanisms qualify. Gate activation on mandatory requirements and their action/decision dependency closure; independent optional blockers remain reported as partial work without blocking qualified mandatory enrollment. Backup is recovery material, never activation. A valid discovery record activates enrollment; there is no inactive flag.

For retained schema-1 requests, the manifest enrollment is `{record,before,requires,qualification}`. `record` is the exact valid startup record (`schema_version`, `project_id`, `clients`, `repository_root`, `git_common_dir`, `policy_digest`, optional `runtime`) and must match selected clients/policy/runtime; do not add an inactive flag. If D3 proposes writing `.vibe-coding-workflow/project.json`, reserve that action for final activation and make its approved full text and mode match `record`; generic writes cannot bypass this. `requires` lists actions needed before activation and must include the dependency closure of every applicable mandatory coverage row; unrelated optional actions need not gate activation, but blocked optional work makes the overall operation partial. `qualification` freezes mandatory requirement IDs and security applicability. Evidence, general/security reviews, task reconciliation, and prior compatibility are supplied later in optional `observations:{manifest_digest,input_digest,qualification,task_reconciliation,prior_compatibility,command_reconciliation}`. For schema 1, `qualification` is one `{requirements,general_review,security_review}` object; `task_reconciliation` and `prior_compatibility` are single evidence-reference objects, nullable where supported; `command_reconciliation` is an optional list. Bind `input_digest` to `runtime.changes.observation_digest(M)`, which covers current checkout/effect fingerprints and modes, enrollment, and package pins. Qualification observations contain requirement `{id,evidence:[{reference,sha256}]}` rows and general/security review evidence. Missing current scoped evidence keeps activation or recovery pending. These are coordinator-verified claims, never helper-observed client execution. For existing enrollment, observations must confirm stopped writers and task/evidence reconciliation; helper independently checks task state with a short read-only SQLite transaction. `command_reconciliation` rows are `{id,attempt_id,stopped:true,evidence:[{reference,sha256}]}`. The command ID must name a D3 command and the attempt ID must match sanitized `command_attempts`. The coordinator verifies termination of that exact command and every writable descendant, bound to the current input and frozen manifest digests. Each launched command remains pending until proof is supplied; if its original plan is unavailable, require manual coordination and do not guess process IDs or kill broadly. Postimages, rollback and idempotent replay cannot be accepted before then. Rollback reactivation needs prior compatibility observation and helper validation of checkout, client, policy and runtime.

For a schema-1 existing-enrollment update, preserve the prior record and ownership. Before every enrollment deactivation, including prepared-receipt recovery and rollback, recheck stopped/reconciled task writers; repeat the check immediately before supporting configuration mutations. Deactivate only the approved, transaction-owned enrollment by staging/removing its active discovery record. Never overwrite/deactivate externally changed enrollment. On rollback, deactivate transaction-owned enrollment first, restore configuration in reverse dependency order, then restore prior enrollment last only after checkout, client, policy and runtime compatibility checks; stale prior records stay inactive. If enrollment changed externally, preserve it and block dependent rollback. Remove only known transaction-created empty parent directories in reverse order; preserve uncertain or nonempty directories.

## Canonical operations

Use [`run_verified_operation(verified_decision, plan_dir, proposal)`](../../../scripts/onboard_coordinator.py) only after independently verifying user or standing authority for the exact operation. The existing owner binds the frozen plan, approval, directories, members and bookkeeping authorities; references and JSON do not authenticate intent. Use the installed [`_validate_scoped`, `_scoped_observation_shape`, `_scoped_input_digest` and `_scoped_qualification`](../../../runtime/changes.py) contracts. Canonical actions carry explicit owners and supported Project resources. Use the actual Project authority path from the approved manifest/acquisition, which may differ from the selected checkout.

Preserve exact approved record postimages/modes, mandatory action dependency closure and independent optional blockers. Genuine owned D4 birth creates an absent canonical database and its original baseline/receipts; task start never substitutes for birth. Bind current input with `changes._scoped_input_digest(manifest)`, covering the actual authority target, package pins and each owner's effect targets. `observation_digest` is schema-1-only.

Optional `observations`, when supplied, is exactly `{manifest_digest,input_digest,qualification,task_reconciliation,prior_compatibility,command_reconciliation}`. All four collections are lists, including empty lists when no proof applies.

| Collection | Row and binding |
| --- | --- |
| `qualification` | `{repository_id,checkout_id,client,requirements,general_review,security_review,scope_observations}`. Requirements contain `{id,evidence:[{reference,sha256}]}`; reviews are evidence lists. Cover the frozen member requirements and applicable security review. `scope_observations:{authority,observation,client,installed}` binds current actual facts; record shape cannot supply native qualification. |
| `task_reconciliation`, `prior_compatibility` | `{repository_id,checkout_id,client,state_dir,evidence}`. Bind the exact affected member/client and authority. `state_dir` is null or canonical absolute path; evidence is a nonempty reference/hash list. |
| `command_reconciliation` | `{id,attempt_id,stopped:true,evidence}`. Bind the exact owner-qualified command ID and retained attempt, with verified termination of that command and every writable descendant. |

Reject unknown or duplicate owners and preserve installed bounds. Unavailable trusted observations remain pending; the coordinator script does not produce native qualification. Resume/rollback requires a newly verified operation decision where applicable, while retaining unchanged approved effects and frozen inputs.

Canonical authority records have per-client configured/active/suspended states. Configuration alone grants no task readiness. Updates and rollback publish owned suspended/postimage states for affected entries, preserving unrelated members; never delete the whole Project authority following the legacy removal procedure. Preserve original bytes, modes, bindings and recovery receipts. Restore prior authority only after fresh compatibility and stopped-writer checks; preserve external edits and uncertain ownership. Later observations cannot silently change an approved configured postimage to active; changed effects require a separately approved operation.

## Completion and remaining qualification

Apply configuration first when safe, even if client qualification evidence is not yet available; that response remains pending (exit 2). When the approved enrollment postimage already permits activation, collect actual proof and resume the same transaction and approval with current-input-bound `observations`; these do not change approved effects or require redundant approval. An approved configured-only postimage requires a separately approved operation to become active. Journal keeps observation history. Rollback may likewise need a newly current-bound prior-compatibility observation after restoring configuration. Configured hooks, an approval record, or a structurally valid enrollment file do not qualify actual client execution. Establish the native evaluation method and smoke cases; perform safe rerun checks, required general review and applicable post-implementation security review. Record package/helper validation separately from actual native client observations. Use an authorized disposable project and temporary enrollment where needed to observe client behavior without enrolling a live project. Keep unobserved mandatory mechanisms unqualified and enrollment incomplete. A restart, login, trust, or other manual external step remains pending until its outcome is observed. Report changed scope, evidence, unresolved interventions and exact recovery/next action; `applied` alone is not project task readiness or merge permission.

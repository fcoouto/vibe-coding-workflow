# Apply and recover an onboarding transaction

Load this guide only for an explicitly authorized `apply`, `resume`, or `rollback`. Apply policy 10, Project Scope and all applicable linked contracts. Use the transaction API schema implemented by the installed package; do not guess fields or adapt a stale example. Public operations are `apply_plan(plan_dir, request)`, `resume_plan(plan_dir, request)`, and `rollback_plan(plan_dir, request)`; the CLI is `onboard apply|resume|rollback --plan-dir PATH` with bounded JSON on stdin. The report is sanitized and contains `transaction_id`, `state`, `completed`, `blocked`, `next_step`, `command_attempts`, `exit_code`, and `limitations`. Resolve package root as the parent of `skills` above this skill.

## Authority and frozen proposal

Before mutation, the coordinator verifies actual user/session authority using trusted host evidence and records its reference. JSON and manifest digests bind artifacts; they cannot authenticate intent. D3 authorization prose is not authority, and no authentication service exists. If authority evidence is unavailable, leave work pending. Require the separately approved D4 manifest to bind the exact D3 plan identity, revision/digest, target checkout, package/source pins, scope and each effect/recovery definition. Reject stale or mismatched inputs before dependent changes. Preserve the plan's Toolkit pin on apply and every recovery; never silently refresh or rewrite the frozen D3 plan. Changing the manifest needs new approval and recovery of the frozen transaction first. Post-apply observations may supplement evidence without changing effects or requiring redundant approval.

Schema 1 requests have `{schema_version:1,manifest,approval}` and optional `observations`; reject unknown fields. The manifest pins `{plan_id,revision,review_digest,current_input_digest}`, canonical `{repository_root,git_dir,git_common_dir}`, D3 `package_pins`, `toolkit_commit`, canonical-source `sources_digest`, `authorization_reference`, the unique full `approved_scope`, ordered `actions`, and `enrollment`. Approval is `{reference,evidence:[{reference,sha256}],manifest_digest}`. The coordinator supplies and verifies host evidence; the helper only verifies artifact binding. The manifest digest is SHA-256 of sorted-key ASCII JSON with compact separators. Required evidence lists must contain valid non-null reference/hash objects.

Each ordered action has `{id,group,resources,preconditions,effects,recovery,execution}`. IDs/order must match D3 and groups must be contiguous; dependencies point to same/earlier groups. Only the exact resource `checkout` is supported. Preconditions bind path fingerprints. Effects are unique relative checkout paths and must match D3 file target/before/after exactly; no overlapping effects, Git metadata, or enrollment paths. Recovery is `file-preimages` or `manual`; only complete file-preimage recovery runs automatically. Writes/deletes and external actions have null `execution`; a command's exact argv must match D3 and has a 1–300 second timeout, plus coordinator evidence for complete effect/recovery qualification and, when replay is needed, proven idempotency. A declaration alone is not a sandbox or proof.

Inspect actual state before each operation. Apply only fresh approved actions and dependencies; transaction-owned results are reconciled from durable receipts, not mistaken for unrelated input drift. Optional actions do not gate enrollment unless required by the dependency closure of a mandatory coverage row; blocked independent optional actions still make the overall operation partial. Do not infer success or failure from missing process/receipt evidence. Return sanitized state, completed and blocked action IDs, command attempts with stable attempt IDs and stopped status, and a concrete next step. Exit 0 means operation completed; 1 means invalid, stale, unsafe or busy; 2 means pending, blocked or partial recovery.

## Transaction safety

The runtime serializes each checkout's transactions with a worktree-specific advisory lock; linked worktrees must not block each other. Commands inherit the lock, and a durable checkout-level unresolved-owner marker blocks other plan directories until command attempts are reconciled. A short journal lock protects durable record access only. The lock does not prevent editors or external tools from changing files. Shared/global effects without suitable resource serialization remain pending for manual coordination. Do not hold D2 task-state SQLite locks during onboarding; for scoped updates, wait for affected task writers to stop and reconcile tasks/evidence first.

Journal the transaction identity, frozen plan pin/digest, authority reference, ordered actions/dependencies, before and intended after states, backups, receipts, observed results, enrollment ownership and state. Keep recovery material outside repositories and instruction-discovery paths, private to the current user. Accept only bounded regular files; reject symlinks and hardlinks. Durable journal updates use same-directory atomic replacement and fsync file plus parent directory before returning. States are `prepared`, `applying`, `interrupted`, `applied`, `blocked`, `rollback_partial`, and `rolled_back`.

For every approved file write/delete, create and flush a durable backup first, including needed metadata such as mode. Safely create missing parent directories with durable transaction ownership records before writing; reconcile them after crashes. Persist and flush a prepared receipt before mutation. Write via same-directory temporary file, fsync contents and metadata, rename, then fsync the parent; delete only after the receipt is durable and fsync the parent. Read back actual state and persist the result. Rollback uses the same durable replacement sequence. On resume/rollback, compare actual state with the original, intended postimage/absence, and durable receipts. Continue only from a recognized state. A `rollback_partial` journal continues with `rollback` after its scoped blockers are reconciled; `resume` continues an interrupted application and cannot proceed until partial rollback is finished. Preserve unknown or user-edited content and block for reconciliation; restore only transaction-owned content still matching the recorded result. Roll back in reverse dependency order and retain backups/journal through partial recovery.

For commands/external actions, the manifest must bound exact effects/resources, preconditions, and a concrete recovery/reconciliation method. Do not execute unbounded effects, use generic command rollback, or blindly rerun after an uncertain crash. Inspect effects/receipts and reconcile the exact command attempt and writable descendants before accepting completion, rollback, or replay; otherwise leave pending with the precise manual reconciliation needed. Missing evidence blocks only dependent actions, so independent authorized work can proceed.

## Apply the Toolkit plan

Use the exact pinned Toolkit procedures and approved D3 actions, preserving complete catalog coverage. Apply installation, update or reuse by compatible dependency groups; use mode-aware configuration, canonical project documents, quality work, integration checks and initial native harness evaluation. Check current versions, changelogs, peers, engines and lockfiles before dependency/configuration changes. Reuse verified equivalents. Preserve product contracts, data, customizations, local edits and the current stack. Do not force installs, apply automatic audit downgrades, add redundant dependencies, or migrate frameworks/providers to match examples. Major incompatibilities, migrations, new costs, destructive changes, and out-of-project effects require specific scoped approval. Keep configuration separate from working integration; follow the relevant policy for quality rules, client integrations, reviews and records. Incomplete pinned sources block only dependent actions.

For file postimages, preserve all unaffected content; an authorized section label does not authorize partial splice semantics. Do not generate a backup before the transaction is approved and started. Safe reruns must not duplicate registrations or erase customizations.

## Enrollment ownership and completion

For new enrollment, stage the active project record outside discovery and install it atomically last, only after applicable mandatory policy changes and mechanisms qualify. Gate activation on mandatory requirements and their action/decision dependency closure; independent optional blockers remain reported as partial work without blocking qualified mandatory enrollment. Backup is recovery material, never activation. A valid discovery record activates enrollment; there is no inactive flag.

The manifest enrollment is `{record,before,requires,qualification}`. `record` is the exact valid startup record (`schema_version`, `project_id`, `clients`, `repository_root`, `git_common_dir`, `policy_digest`, optional `runtime`) and must match selected clients/policy/runtime; do not add an inactive flag. If D3 proposes writing `.vibe-coding-workflow/project.json`, reserve that action for final activation and make its approved full text and mode match `record`; generic writes cannot bypass this. `requires` lists actions needed before activation and must include the dependency closure of every applicable mandatory coverage row; unrelated optional actions need not gate activation, but blocked optional work makes the overall operation partial. `qualification` freezes mandatory requirement IDs and security applicability. Evidence, general/security reviews, task reconciliation, and prior compatibility are supplied later in optional `observations:{manifest_digest,input_digest,qualification,task_reconciliation,prior_compatibility,command_reconciliation}`. Bind `input_digest` to `runtime.changes.observation_digest(M)`, which covers current checkout/effect fingerprints and modes, enrollment, and package pins. Qualification observations contain requirement `{id,evidence:[{reference,sha256}]}` rows and general/security review evidence. Missing current scoped evidence keeps activation or recovery pending. These are coordinator-verified claims, never helper-observed client execution. For existing enrollment, observations must confirm stopped writers and task/evidence reconciliation; helper independently checks task state with a short read-only SQLite transaction. `command_reconciliation` rows are `{id,attempt_id,stopped:true,evidence:[{reference,sha256}]}`. The command ID must name a D3 command and the attempt ID must match sanitized `command_attempts`. The coordinator verifies termination of that exact command and every writable descendant, bound to the current input and frozen manifest digests. Each launched command remains pending until proof is supplied; if its original plan is unavailable, require manual coordination and do not guess process IDs or kill broadly. Postimages, rollback and idempotent replay cannot be accepted before then. Rollback reactivation needs prior compatibility observation and helper validation of checkout, client, policy and runtime.

For an existing-enrollment update, preserve the prior record and ownership. Before every enrollment deactivation, including prepared-receipt recovery and rollback, recheck stopped/reconciled task writers; repeat the check immediately before supporting configuration mutations. Deactivate only the approved, transaction-owned enrollment by staging/removing its active discovery record. Never overwrite/deactivate externally changed enrollment. On rollback, deactivate transaction-owned enrollment first, restore configuration in reverse dependency order, then restore prior enrollment last only after checkout, client, policy and runtime compatibility checks; stale prior records stay inactive. If enrollment changed externally, preserve it and block dependent rollback. Remove only known transaction-created empty parent directories in reverse order; preserve uncertain or nonempty directories.

Apply configuration first when safe, even if client qualification evidence is not yet available; that response remains pending (exit 2). Then collect actual proof and resume the same transaction and approval with current-input-bound `observations`; this does not change approved effects or require redundant approval. Journal keeps observation history. Rollback may likewise need a newly current-bound prior-compatibility observation after restoring configuration. Configured hooks, an approval record, or a structurally valid enrollment file do not qualify actual client execution. Establish the native evaluation method and smoke cases; perform safe rerun checks, required general review and applicable post-implementation security review. Record package/helper validation separately from actual native client observations. Use an authorized disposable project and temporary enrollment where needed to observe client behavior without enrolling a live project. Keep unobserved mandatory mechanisms unqualified and enrollment incomplete. A restart, login, trust, or other manual external step remains pending until its outcome is observed. Report changed scope, evidence, unresolved interventions and exact recovery/next action; `applied` alone is not project task readiness or merge permission.

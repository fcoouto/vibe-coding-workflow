# Qualification and activation

Load only for an explicitly selected managed activation or maintainer/adapter qualification. Ordinary project onboarding and native editing do not require this campaign. Keep its prerequisite evidence and limits scoped to the selected capability.

## Activation and reporting

### Staged disposable qualification

Use staged acceptance only for an explicitly approved disposable qualification target. Ordinary projects and the primary pilot retain full activation prerequisites. Observe the actual selected frontend, source identity, relevant configuration and host safety before startup acceptance. These observations do not establish the Toolkit bound-task guard, PostToolUse, Stop, Interrupt or other unobserved behaviors. Keep all nine behavior cases and the complete actual manifest/catalog requirements recorded as verified, pending or evidenced inapplicable; the pilot's 44 requirements are not a product-wide fixed count.

Pass genuine Native-issued frontend witnesses and independently verified assessments separately from proposal JSON. The existing D4 owner retains immutable setup receipts and approved attempt scope in its private journal. Each upgrade uses a new exact D4 operation and references its predecessor; preserve original receipts, source pins and recovery material. Later startup compares bounded local observable configuration, without native subprocesses or per-session frontend proof.

For vendor-owned native state, use `CoordinatorOperationOwner.observe_native_source(identity, attempt_ref, observer)` with the independently verified original allocation, explicit external effects and manual serialization. The same D4 journal retains its claim before the owner launches the exact child; failures consume the allocation and unresolved identified writers retain exclusion. Reconcile that exact process and relevant writers through `reconcile_native_source` under the bounded source-observation guarantee below. This path grants no project-file recovery exemption. Retained managed command observations keep their original effect and recovery rules.

The CLI keeps closed stdin and retains only its actual header/source, executable and non-secret launch facts. A separately approved metadata allocation and pinned journal may consume the reconciled CLI reference. Its app-server reads only the existing CLI thread and actual registration/configuration origins; it cannot create or resume a thread. Keep raw metadata transient and retain only Core's filtered setup observation. Native hook enumeration can initialize user `.hook-trust` baselines, including unrelated enumerated plugins. The actual campaign must authorize those vendor-owned effects; source implementation or repository-local command authorization supplies no permission to execute them.

When a disposable `bounded-native-source-v1` attempt needs to suppress inherited user hooks, bind one `-c 'hooks.state={...}'` argument in each approved argv. Use `exec --json --sandbox read-only` for the bootstrap and `app-server --listen stdio://` for the metadata reader, with the flag after the subcommand options. Each entry names an actual inherited user hook and sets only `enabled=false`. Use the same map in both launches. Metadata must confirm the map, disabled competing hooks, and the exact enabled, trusted candidate registrations. Keep candidate enablement and trust file-backed. The original no-override launch remains available.

The trusted coordinator supplies `qualification_scope` separately from proposal JSON. Only its exact live callback process can acquire observation authority. For this bounded source-observation path, verify that exact native CLI/API process exited and was reaped, then reconcile workflow-directed project writers and every identified conflicting or uncertain writer. Client-managed startup descendants remain unknown and may cause late effects; do not represent them as stopped or exclude a workflow hook or operation as generic background work. A pending workflow hook, unexpected tool/spawn, unexplained write, conflict or uncertain identified writer blocks affected work. Opt in only when the original verified allocation explicitly sets `native_execution.source_contract='bounded-native-source-v1'`; its proofs record observed facts and identified writers, not a complete inventory or empty child set, actual unexpected calls still block dependent acceptance, and absence preserves legacy full-stop semantics. Use a distinguishable limited record for new observations; never claim that all descendants stopped merely to pass the reader, or auto-upgrade legacy records. `collect_setup` consumes Native's private witness plus independently verified assessment. New external observations use the existing journal's `native_observations` claims; preserve older `command.setup_capture` and full setup receipts unchanged. After exact process and identified-writer reconciliation, `collect_retained_setup` constructs a successor for a separately verified activation operation. Preserve original native transactions and typed source references; a full receipt predecessor references only another full setup receipt. Never alter the approved manifest to insert a learned receipt hash.

This limited closure does not certify shared native-state quiescence: vendor-state effects still need explicit authorization and the required serialized window. Preserve the disposable fixture and native-home state; do not automatically delete the fixture or roll back the native home. D4 command recovery/replay, D5 checks, D6 worker/reviewer reconciliation, READY, merge and full-catalog requirements retain their existing guarantees.

Bootstrap acceptance requires actual native frontend/configuration provenance, the source-backed submitted-write policy rejection and independent original writable-canary before/after facts. Claim only that native policy rejected the submitted write: this does not prove effective-input identity, protection of a particular canary or local operating-system enforcement. Keep this native safety assessment separate from all nine Toolkit cases. Qualification-only SessionStart supplies restricted context and creates no task or title-repair effect. A selected managed workflow must meet its applicable startup/pre-tool requirements, and editing controls additionally require post-tool behavior. These requirements do not gate ordinary native editing, tests or review. Supported managed observations use the actual parent task stream, retained assignment before-artifact and independently read receipts/generation; child-stream behavior remains pending.

For staged D5 review readiness, the trusted coordinator calls `runtime.setup_readiness.observe` with the original qualification task identity and revision, plus exact `check_attempt_id` and `review_attempt_id`. Run the registered check, independent native review, reconciliation and completion verifier through their existing owners first. The observer rechecks the current candidate, settled claims and latest native review without launching another turn. Pass the issued observation as `readiness` to `collect_retained_setup` for a separately verified successor. This evidence covers review readiness only. Other capabilities and the task's qualification purpose retain their original requirements.

Until a selected Toolkit guard is genuinely verified, admit only its exact bounded qualification attempt. Pending capabilities block only dependent managed use. Bind the attempt to the approved disposable repository/checkout, actual task and native identities, permitted operations, original finite budgets, claims and stopping condition. Admission uses existing task/assignment accounting; it cannot reset consumed limits. Expiry, exhaustion or interruption stops further effects, preserves uncertain writer claims and requires separately authorized recovery.

A qualification task keeps its purpose even after capability evidence improves. Canary outcomes may support only their verified qualification entries; they cannot become ordinary READY, DONE, publication, merge or primary activation authority. Successful managed activation requires its applicable requirements, reviews and any selected repository enforcement. Report startup acceptance, pending capabilities and basic onboarding separately.

Selected managed activation requires qualified applicable adoption and native mechanisms, plus repository enforcement when that capability is selected. Configured hooks, valid record shape and stored labels do not prove actual client execution. Use an authorized disposable scope for native evaluation; preserve its actual budgets and settings. Report package/helper validation separately from native observations.

For selected Codex activation, use the [approved activation guarantee](../../../policies/01-project-scope.md#authority-and-activation): preserve actual setup behavioral evidence and compare later observable configuration. Do not claim proof of each later session's loaded controls or repeat setup solely because a new session starts. A changed or missing required observation leaves dependent activation pending.

Canonical activation observations use `{manifest_digest,input_digest,qualification,task_reconciliation,prior_compatibility,command_reconciliation}`. All four collections are lists. Bind current input through `changes._scoped_input_digest(manifest)`. Each qualification row names `repository_id`, `checkout_id`, `client`, requirement evidence, general/security review evidence and `scope_observations`. Reconciliation rows bind the affected member, state directory and evidence; command rows bind `id`, `attempt_id`, `stopped:true` and evidence. Follow the installed `_scoped_observation_shape` and `_scoped_qualification` schemas. Observations supplement evidence; they cannot change approved effects.

An approved configured postimage needs a separate exact activation operation. Verify that existing onboarding authority covers its effects, including any runtime allocation; ask only when the authority rules identify a missing material decision. Never widen the original frozen manifest or reuse its effect digest for changed effects. An already approved active postimage may resume with fresh qualification observations under its existing approval. Missing mandatory activation evidence returns pending, not a false success. Native restart, login or trust interventions remain pending until observed. These instructions do not supply the production qualification reader or substitute recorded claims for trusted observations.

Update the [Reviewed Configuration](reviewed-configuration.md) with actual changes, preserved conflicts, operation state and the next required action. Exit 0 means the selected operation completed; nonzero means invalid, blocked or partial work. Successful configuration or rollback does not mean runtime activation, qualified client execution or merge readiness.
